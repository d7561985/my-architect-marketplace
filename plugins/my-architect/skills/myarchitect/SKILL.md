# myarchitect — proactive backlog tracker

Кодифицирует четыре вещи поверх любого проекта, использующего MCP-сервер `my_architect`:

1. **Архитектор — живой источник истины, а не журнал постфактум.** Берёшь задачу — сперва читаешь ноду и её доки, ведёшь работу против них и держишь их в актуальном состоянии, пока работаешь (не только на старте и финише).
2. Любой surfaced gap (deferred / caveat / known issue / "to be tested when") отслеживается в Архитекторе **до конца текущего хода**: долг — нодой, названная пользователем/мейнтейнером проблема — issue без обязательного эпика; решение связывается через `closes`.
3. Рутинные обратимые решения в разрешённом scope агент принимает по источникам и сохраняет основание. Реальный конфликт смысла, изменение целей/приоритетов или недостающие полномочия требуют точечного решения человека; независимая работа продолжается.
4. Реализация поведения идёт с TDD/Trace по самодостаточной процедуре плагина и правилам проекта; внешние skills — необязательные расширения. Перед закрытием проверяется цепочка требование → постоянный тест → CI. Выполненные требования получают явный `done`; issue закрывается только когда **все** closing-элементы завершены: требования/обычные узлы `done`, managed узлы с явным `delivered: true` (`approved` не равен `done`). Затем обновляются производный индекс и валидация.

Skill универсальный: project ID, эпики, релизы, уровни иерархии и конвенции тайтлов читаются из текущего проекта, а не захардкожены.

## Первый вход — безопасный discovery и выбор масштаба

**Для каждого впервые проверяемого/неизвестного legacy-проекта безопасное чтение предшествует общему `get_project_context` и init.** Установи точный pid по [setup.md](references/setup.md). Проверь доступный каталог/поддержку через безопасные readers; для legacy-источников используй [safe audit](references/product-migration.md). Обычный project/hierarchy GET на старом backend может ремонтировать storage; init/doctor/validate/sync не служат probe. Ошибка/404 не равна пустой структуре. При неизвестной поддержке сохрани partial context и точное ограничение, не подменяй безопасный intake ремонтом.

Если discovery показывает несопоставленную работу, отсутствующие продуктовые области/связи или неразделённые current/proposed, самостоятельно выполни обоснованную **additive adoption в разрешённом scope текущей задачи** по [migration-adoption.md](references/migration-adoption.md). Отдельное слово «миграция» или `/migrate` не требуется. Это не поручение без разбора переделать весь live-проект: сохраняй чужие данные, broader scope и спорные источники как адресный остаток. При явно порученной организации всего проекта маршрут охватывает объявленный проект; read-only запрос всегда остаётся read-only.

Маршрут: safe discovery → источники и глобальное сопоставление → самостоятельная классификация → [compose/prepare/review/apply/verify](references/migration-package.md) → спецификации, активная работа и scoped handoff. Агент выводит обоснованные области и соответствия из фактов; заранее утверждённая карта и готовый пакет от пользователя не обязательны. Эскалируй реальные смысловые конфликты, изменение целей/приоритетов или нехватку полномочий; независимую разрешённую часть продолжай. Runtime capability и сохранённые policy проверяются отдельно: согласие в разговоре не записывает их автоматически.

## Setup — выбрать проект и сохранить связь с репозиторием

Для обычной работы (после выбора маршрута выше), при первом обращении к проекту и в `/my-architect:init` прочитай [references/setup.md](references/setup.md).

1. Прочитай `CLAUDE.md` и `.architect/traceability.json`: используй согласованный явный `pid`/`projectId` или уже сделанный пользователем выбор. Конфликт ID требует уточнения до записи.
2. Если связи нет, получи `list_projects` и предложи выбрать существующий проект или создать новый. Даже единственный или первый результат не доказывает связь с репозиторием. Ошибка запроса не означает пустой список.
3. Создание выполняй по явному решению пользователя, с согласованными именем и `preset`, без sample content. Уже данное разрешение повторно не запрашивай.
4. Проверь выбранный/возвращённый ID безопасным фактическим reader (catalog/safe audit) по setup reference, сохрани его точно в локальной привязке и продолжи `/my-architect:init`. Пользователь не обязан знать `pid` заранее; для MCP-операций с проектом он обязателен. Полная процедура и обработка незавершённой настройки — в setup reference.

Используй подтверждённую связь в следующих сессиях без повторного выбора. Отсутствие `.architect/` означает отсутствие локальной настройки, а не отсутствие проекта на сервере.

## When this fires

Триггеры из пользовательской речи живут в `description` (frontmatter) — RU+EN, «deferred / отложил / caveat / known issue / не подключено / is this tracked? / что дальше?» и т.п. Помимо них, **сам себя триггеришь**, когда:

- Закрыл feature через `complete_task` или сказал «feature done / shipped».
- Написал commit body или acceptance report со списком follow-ups / deferreds / «out of scope» / «what's NOT covered».
- Упомянул будущий триггер («at scale», «when paid users arrive», «next tier»).
- Починил случайный баг по дороге, не зафайлив его.
- **Берёшься за работу по трекаемой ноде** (`start_task`, «беру/реализую <фичу>»), по ходу поменялось понимание фичи, или формируешь новую фичу/эпик с нуля.
- Обсуждается структурная работа, для которой не решено «делать ли» — гейт (шаг 0), не молчаливое оформление.

**Когда НЕ загружать.** Чисто разговорный ход или тривиальная правка, не связанная ни с одной трекаемой нодой.

## Первый вызов с `pid` — после Setup

Первый/неизвестный legacy intake использует безопасный discovery из маршрута выше. Общий context не обязателен для проверки связи и допустим только при подтверждённом отсутствии repair side effects. Поручение на adoption не разрешает неявный ремонт исходника; для intake используй safe audit, для выбранной работы — адресные readers. При уже подтверждённой привязке и явном target переходи к [scoped-context.md](references/scoped-context.md) без повторного общего dump. При Setup используется:

```
mcp__my-architect__get_project_context({ pid: "<resolved-pid>" })
```

Один вызов даёт `meta + hierarchy + backlog + diagrams + stats`. Это общий legacy overview, не обязательный полный аудит перед каждым изменением. Для уже подтверждённой привязки и выбранной работы используй [адресный контекст](references/scoped-context.md); возобновление проверяет свежий snapshot даже без собственных create/update. Не подменяй им полный migration inventory или подтверждение claim.

Каталог продукта читается отдельно по [product-catalog.md](references/product-catalog.md), если новый MCP-инструмент доступен. Успешный удалённый `get_product_catalog` подтверждает чтение: недоступность не равна пустому каталогу. Нормализованный `catalog.schemaVersion: 2` не доказывает запись v2: сохрани `remoteSchemaVersion`, при 1/неизвестном останови такие записи. Поиск постоянной фичи по умолчанию глобальный через `search_product_features`; выбранная ветка UI не сужает контекст агента. Старый сервер сохраняет прежний workflow; записи каталога при ошибке чтения запрещены.

Для выбора/продолжения работы отдельно проверь удалённый flow по [epic-flow.md](references/epic-flow.md). `get_project_context.epicFlow` — компактный контекст, legacy stats не показывают поставку. Managed epic сначала получает подтверждённый claim; дочерний `get_next_task` требует `scopeEpicId`, `claimId`, `assignee`. HTTP 404 не означает пустую очередь и не разрешает legacy bypass. `complete_task` закрывает обычную дочернюю работу, а review/delivery управляемого эпика идут через `apply_epic_flow_command`. Перед новой confirmation прочитай `get_epic_flow_capabilities`: совместимый сервер может установить automation identity MCP-ключа, которую передают как actor новой confirmation по фактически принятой policy. Обычный cookie/local вызов не является явным account action; интерактивное подтверждение использует отдельный поддерживаемый endpoint. Это не доказательство физического присутствия человека; capability не принимает policy за владельца и не меняет сохранённый retry payload.

## Feature lifecycle — the map (router)

Жизненный цикл фичи, по порядку. Буквы воркфлоу исторические (на них ссылаются слэш-команды) — последовательность задаёт **эта карта, не алфавит**. Тела всех воркфлоу — в [`references/workflows.md`](references/workflows.md); открой нужный, когда дошёл до шага.

Ниже feature означает **узел работы**. Постоянная product feature живёт в отдельном каталоге: сначала найди существующую возможность и опиши дельту эпика, затем декомпозируй работу. Новая задача не создаёт автоматически новую продуктовую фичу. `accepted`-классификация требует обоснованного применимого решения в порученном scope (агента либо владельца), `available` — доказанного текущего поведения; статус done в дереве не заменяет ни одно из них.

**Intake перед выбором workflow.** Прочитай [product-evolution.md](references/product-evolution.md): после глобального discovery различи `new` (новая возможность), `change` (изменение существующей), `fix` (исправление отклонения от подтверждённого поведения) и `technical` (техническая работа). Для существующей фичи сохраняй stable ID и дочитывай current/base/proposed и все обязательные ограничения по [scoped-context.md](references/scoped-context.md). `technical` может иметь product/area/architecture scope без выдуманной фичи или пользовательского сценария. Продолжение существующей работы не запускает повторное создание узлов или уже пройденное согласование; свежая сверка определяет изменившуюся дельту. До реализации свяжи разрешённое изменение с work ID и точной базой, при закрытии отдельно проверь поставку среза через evolution и поставку managed epic через flow.

0. **Decide → Workflow I** — для структурной работы, где ещё не решено «делать ли», проясни ценность и границы по 7 вопросам; используй известные ответы, спроси только недостающие решения. Уже порученную реализацию не возвращай на повторный апрув из-за размера или межсервисного контракта. Легитимны «не делаем» и «не сейчас + триггер». Обычная работа идёт в Z/D. BO-review (`/my-architect:bo-review`) — адресная проверка текста по необходимости, не обязательная церемония каждого эпика.
1. **Create → Workflow Z** — до кода сохрани минимальную полезную работу, требования и связи с продуктом, затем `validate_project` и проверенные ID. Каждый блок имеет самостоятельный наблюдаемый результат; слой кода сам по себе не требует отдельного узла. Один результат допускает одну ноду, если preset это поддерживает. Декомпозиция и проверки granularity — [forming-nodes.md](references/forming-nodes.md).
2. **Work → Workflow D** — проверить flow/claim по [epic-flow.md](references/epic-flow.md), затем discovery → явный work target → обязательные requirements/pages/details по [scoped-context.md](references/scoped-context.md) ДО кода. При возобновлении проверить fresh token, по ходу держать источники актуальными. Недоступный reader явно ограничивает fallback, не превращается в пустой успешный brief. Сложный brief с несколькими применимыми источниками/variants/сквозными правилами перед заявлением о полноте проходит независимый review → один repair → preservation check по [context-coverage-review.md](references/context-coverage-review.md); недоступность исполнителя остаётся явной, не создаёт human gate.
3. **Trace → [traceability.md](references/traceability.md)** — постоянный тест декларирует требование, гейт видит эту связь и исполняется в CI; чувствительность проверена мутацией. Пропуски — явные waivers, не молчание. Команды берутся из local `CLAUDE.md`.
4. **Close → Workflow A** — после Trace: обычная работа через `complete_task`, managed epic через review и поддерживаемую принятую delivery policy; затем подтверждённые требования/issue, validate и scan-for-gaps. Done детей не поставляет эпик.
5. **File deferred → Workflow B** — каждый всплывший долг становится нодой: de-dup → parent epic → priority/release (rubric) → `build_hierarchy` → validate. Зарегистрированные проблемы хранятся как issue, связь решения — `closes`.
- **Docs → Workflow C** — сквозной источник истины; вплетается в Z (создание) и D (работа).

Authoring **ведёт** цикл — фичу формируешь ДО кода, а не дописываешь ноды постфактум.

**Диаграммы по задаче.** Event Storming полезен, когда есть риск пропустить события, состояния, порядок или взаимодействия акторов/сервисов. WBS показывает полезную декомпозицию выбранной работы; USM — реальный пользовательский сценарий и срезы. Агент выбирает минимальное представление, которое снимает эту неопределённость; название «эпик» не требует новой диаграммы, подпроекта или повторного моделирования уже понятного потока. При выбранном Event Storming используй поддерживаемый канвас и проверь `sequence`; исправь реальные бреши или сохрани открытый вопрос, не выдумывай связи ради зелёной схемы. Детали — [forming-nodes.md](references/forming-nodes.md).

**Ship = sync (нет отложенного статуса).** Фактическая отгрузка в ТОМ ЖЕ ходу проходит Workflow A: доказанные требования явно `done` → свежее состояние работы и `get_issues` → issue `closed` только при непустом `closedBy` и завершении **всех** closing-элементов (managed node: `delivered: true`; остальные: `done`) → синк индекса → `validate_project`. Для managed epic delivery подтверждается только flow, legacy done не достаточно; отсутствие policy/verifier остаётся явным незавершённым шагом. `complete_task` обычной работы не обновляет требования/issue и не каскадирует поставку managed epic. Частичное решение оставляет проблему открытой. Если отгрузка не привязана ни к одной ноде — это сигнал пропущенного Workflow Z. Подготовленная локальная/preview-версия не является опубликованным релизом.

## Decision rubric

Для решений при intake и ведении работы (в том числе `Priority + release` в Z/B):

| Lane | Сигналы | Действие |
|---|---|---|
| **Tech-debt только что закрытой фичи** | Broken plumbing, dropped reference, retry path не подключен, length/style guard пропущен, FP rate caveat. Всегда привязано к feature, который только что закрылся. | Префикс типа `P3-tech-debt:` (или конвенция из local CLAUDE.md), тот же эпик, релиз = релиз родителя. **No ask.** |
| **Future enhancement с явным триггером** | «at scale», «when paid users arrive», «if FP > X%», «next tier», «когда появится N юзеров». Триггер observable. | Новый feature-нода, последний/будущий релиз, триггер прописан в описании. **No ask.** |
| **Реальный смысловой конфликт / цели / приоритет / полномочия** | Доступные источники не определяют нужный исход, выбор меняет согласованную цель/приоритет, либо действие выходит за поручение. | Сохрани конкретный спорный выбор и последствия; запроси только недостающее решение. Останови зависимое действие, продолжай независимую разрешённую часть. |

Сначала проверь источники и уже данное поручение. Обратимое оформление, название, путь документа и однозначная классификация — решения агента в scope с кратким основанием; не вопросы человеку по умолчанию. Неизвестный приоритет/релиз можно оставить явно не назначенным, не выдумывая обязательство. Неполные данные не дают права менять цель или policy. Read-only поручение остаётся read-only; accepted classification не подтверждает availability, поставку или account decision.

## Don't

- **`delete_node`** — irreversible. Для managed epic сохраняй ID/history и используй разрешённый wait/cancel через flow; не заменяй описание причиной и не обходи guard. Для unmanaged работы фиксируй проблему без потери исходного scope.
- **Skip de-dup** — дубликаты в backlog ломают приоритизацию `get_next_task`.
- **Ask twice** — если rubric говорит «no ask», не спрашивать. Пользователь ценит проактивность на routine.
- **Хардкодить эпики / релизы / конвенции** в самом skill — читать live из `get_project_context` и local `CLAUDE.md`. Skill универсальный, проектные данные живут в проекте.
- **Restate local `CLAUDE.md`** — он всегда в контексте, дублировать в skill = дрейф. Reference, don't duplicate.
- **Не оставлять ноду/доку устаревшей.** Разошлась работа с тем, что записано — синхронизировать в том же ходу (`update_doc` / `update_node` без managed status/assignee) и зафиксировать unresolved wait в flow, если нужно. Изменённый scope/requirements требует актуальной review, не подмены baseline.
- **Не обходить Workflow A прямым `done`.** Ни bulk-закрытие нод, ни старый `approved`, ни waiver не заменяют доказательства исполнения требований и синхронизацию issue. Порядок и условие **всех** closing-элементов — в Workflow A; отложенного «issue и индекс поправлю потом» нет.
- **Не возводить непроверенную интеграцию в узел.** «X читает через Y», «завязано на сервис Z» — проверь по коду ДО создания ноды; не подтвердилось → draft с маркером `VERIFY:` в описании, не уверенный блок. `validate_project` ловит целостность, не выдумку. (Детали — [`references/forming-nodes.md`](references/forming-nodes.md) → Verify before you elevate.)

## Composes with

- **TDD/Trace** — самодостаточный минимум в [traceability.md](references/traceability.md). Доступный `superpowers:test-driven-development` можно использовать как расширение; отсутствие стороннего skill не блокирует работу. Явные требования проекта к TDD, CI и доказательствам сохраняются.
- **Проверка перед завершением** — выполни Trace и перечитай результат до заявления о готовности. Доступный `superpowers:verification-before-completion` может помочь; отдельный бренд skill не является условием закрытия.
- **Делегация** — используй доступных host-агентов, если независимая часть экономит время или улучшает проверку. `superpowers:dispatching-parallel-agents` — необязательная помощь; число найденных записей само по себе не требует нового агента.
- **`recursive-context`** (этот же плагин) — oversized-входы: гигантский лог/дамп/транскрипт или whole-repo задача → декомпозиция вместо чтения в лоб; для Workflow Z шаг 3 / Workflow I шаг 3 добывает факты с путями (рецепт requirements-mining).
- **Граф кода — перед любой фазой Discovery.** Есть `graphify-out/graph.json` (проверка — один `Bash`-вызов) → ориентация идёт запросом к графу, и только потом `grep`/`Read`/`Workflow`/fan-out. Порядок и его границы — `recursive-context` → [`references/code-graph.md`](../recursive-context/references/code-graph.md), раздел «Композиция». Плагин ставит SessionStart-хук, который сообщает о наличии и свежести графа сам; если сообщения не было — проверь руками, хук молчит и когда графа нет.
- **`design` (этот же плагин)** — когда решение ещё нужно спроектировать. Сохраняет global discovery, адресный current/base/proposed, границы поручения и один канон спеки. Рутинный дизайн в согласованном scope не требует повторного апрува; при использовании внешнего brainstorming сохраняй эти правила. Перед кодом — Z для отсутствующей работы или D для существующей; отдельный файл плана нужен по сложности, а не по названию команды.
- **Диагностика повторных неудач** — пересмотри гипотезу и источники; доступный `superpowers:systematic-debugging` необязателен. Если требуется изменение цели/контракта вне поручения, адресно вынеси решение; не превращай любой третий фикс в новую инициативу.
- **Завершение ветки** — merge/PR фиксируется с доказательствами в том же ходу (ship = sync), независимо от наличия `superpowers:finishing-a-development-branch`. Managed epic идёт через review/policy из epic-flow; merge не равен delivery.
