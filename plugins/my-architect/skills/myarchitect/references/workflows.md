# Workflows Z / D / A / B / C / I / R — full bodies

The [Feature-lifecycle map in SKILL.md](../SKILL.md) routes here. The letters are historical (slash commands reference them); the **map** defines the sequence, not the alphabet. Read the relevant workflow when you reach that lifecycle step.

- **Create → Workflow Z** · **Work → Workflow D** · **Trace → [traceability.md](traceability.md)** · **Close → Workflow A** · **File deferred → Workflow B** · **Docs → Workflow C** (cross-cutting) · **Decide (initiative) → Workflow I** · **BO-review → Workflow R**

Node-forming mechanics (preset levels, title lint, `build_hierarchy`, reclassification) live in [forming-nodes.md](forming-nodes.md).

**Managed epic override.** Before work selection, start, waiting or closure, read [epic-flow.md](epic-flow.md). Flow owns managed epic stage/claim/review/delivery; the legacy task steps below apply to ordinary work nodes. Never substitute legacy/bulk/move/full-replace writes for a rejected flow command. Creation in Z/I/B does not automatically enqueue or claim an epic.

**Product evolution intake.** Before Z/D, follow [product-evolution.md](product-evolution.md): global discovery, explicit new/change/fix/technical intent, complete current/base/proposed context, then a sourced proposal tied to the existing or newly authorized work ID. Reuse an existing feature and work node when applicable. Technical scope does not require a synthetic product feature or scenario. Before A, verify the independently delivered slice and exact evidence there; legacy status and epic delivery remain separate.

## Workflow Z — Authoring a feature from scratch (CREATE)

Превращает prose-описание в спецированную фичу-ноду **до кода**. Это вход в цикл; не путать с Workflow B (тот — про долги уже existing/закрытой работы).

0. **Существующая возможность продукта.** Выполни discovery/read из [product-catalog.md](product-catalog.md). При поддержке каталога сначала найди постоянную product feature и опиши, что работа создаёт/меняет/выводит; новый эпик или RFC не требует нового product feature ID. Если соответствие неясно — предложение с источниками, не принятая классификация. Каталог недоступен → обозначь ограничение и продолжай прежний workflow в разрешённом объёме, без каталожной записи. После глобального discovery прочитай адресный контекст найденной фичи по [scoped-context.md](scoped-context.md): весь обязательный manifest требований и точные записи с одним snapshot token до формирования новой приёмки. До появления work ID используй существующий product-feature target; если фичи ещё нет, не выдумывай ID ради reader. Вложенная Product Map, предлагаемое размещение и явные пробелы остаются обязательными.

1. **Prose → spec.** Из запроса и источников выдели исход, потребителя, приёмку и ограничения. До solution-specific спеки и декомпозиции проверь существующие решения целиком или по частям по [solution-discovery.md](solution-discovery.md); используй применимый прежний выбор, иначе сравни обоснованные пути и сохрани основание. Прочитай недостающее адресно; рутинное оформление выбери сам. Не выводимое из фактов смысловое решение эскалируй по rubric, сохраняя независимую работу.

2. **Минимальная полезная структура** — используй существующую работу либо `build_hierarchy` по живым `levelNames`/preset. Один результат — одна нода, когда схема это поддерживает; дочерние узлы нужны для самостоятельной приёмки, поставки или владения. Если схема требует контейнер, сохрани обязательный уровень без дополнительного слоя одинаковых описаний. Не выдумывай уровень вне preset и не дроби работу по файлам или числу коммитов.

   Существующее дерево и IDs сохраняются. Новое правило не разрешает удалять старые узлы, переносить чужую работу или обходить managed flow. Warning `status-rollup-lag` требует проверки фактического состояния, а не создания фиктивного ребёнка.

3. **Upfront-требования** (не «потом»). У фичи с тестируемой приёмкой — `add_requirement` сразу на feature-ноду:
   - `FR` — поведение («что система делает»);
   - `NFR` — качество/SLO («как быстро/надёжно»);
   - `SAR` — архитектурное ограничение («что трогаем/не трогаем, где живёт»);
   - `CON` — hard-ограничение («чего нельзя»).

   **Четыре правила гейта** на каждое требование и description (стоп-лист и правила — [initiative-gate.md](initiative-gate.md)):
   - потребитель поимённо (фича / KR / команда) — нет потребителя, нет фичи (YAGNI);
   - ценность не заканчивается артефактом — «Сделаем X → актор сможет Y → увидим по Z» (актор + новое поведение + сигнал);
   - модальность ЦЕЛЬ/СЕЙЧАС — целевые числа и состояния помечены как цель, не поданы как текущее;
   - description ноды — прогнать по стоп-листу.

   Если потребитель/исход не определён даже после чтения применимых источников, сохрани конкретный пробел и спроси о нём; не заполняй его правдоподобной выдумкой.

   **Факты из кода.** Репозиторий доступен → перед формированием требований добудь факты скилом `recursive-context` (рецепт requirements-mining; на уровне main loop, до диспатча агентов): «что уже работает и не трогаем», потребители API — с путями-доказательствами. Факт без пути в код — не факт.

   Требования — **часть описания фичи**, а не довесок к долгам. Проверь ответ (созданные ID).

4. **Дока, если логика нетривиальна** — `create_doc({nodeId})` (Workflow C). Лидируй фактом, добавь **Source** (чат-ход/спека), чтобы на доку можно было опираться позже. Влезает в description — не плоди файл.

5. **Релиз + приоритет.** Сохрани принятые значения; неизвестное оставь явно не назначенным. Для обоснованных 2+ обновлений используй `bulk_update_nodes` и проверь `successful`/`failed`. Реально конфликтующий выбор — адресное решение по rubric, не остановка всей независимой работы.

6. **Проверить результат, не «записал молча».** `validate_project` → чисто; перечисли созданные ID (фича / стори / требования / док). Если каталог поддерживается и соответствие авторизовано, свяжи фактически созданные work node IDs с постоянными фичами через `impacts` по versioned write из [product-catalog.md](product-catalog.md), сохраняя остальные записи. Если запись не подтверждена, явно укажи неподтверждённую связь; существующую ноду не создавай повторно. Только после проверки фича работы «заведена»; это не статус available постоянной фичи.

**Когда дробить:**

- *Feature → stories*: приёмка распадается на независимые «и…, и…», несколько ролей/флоу, или не влезает в один заход.
- *Story → tasks*: есть самостоятельная проверка, поставка или отдельный исполнитель; файлы, компоненты и число коммитов сами по себе не причина.
- *Один результат*: минимальная допустимая preset нода; шаги реализации остаются в описании/плане. Дроби дальше, когда появился реальный независимый срез.

## Workflow D — Working a task against the architect (WORK · живой источник истины)

Архитектор — то, против чего ведёшь работу и что держишь актуальным, а не запись постфактум.

0. **Scope и владение.** Проверь capability и текущее состояние flow. Продолжи разрешённый owned claim либо получи server recommendation и подтверждённый claim по [epic-flow.md](epic-flow.md). Дочерний `get_next_task` в managed проекте требует актуальные `scopeEpicId`, `claimId`, `assignee`; отсутствующий/чужой/waiting claim не разрешает глобальный fallback. Read-only discovery не требует claim, исполнение managed scope — требует. При ожидании используй wait с причиной/ответственным/следующим шагом, сохраняя stage и claim.

1. **Перед кодом и при продолжении** — после глобального discovery по [product-catalog.md](product-catalog.md) прочитай выбранную работу через `{kind:'work',id:nodeId}` по [scoped-context.md](scoped-context.md). Дочитай все страницы обязательного requirements manifest, точные записи требований и относящиеся docs/impacts/issues через token-pinned detail windows; summary не является прочитанной приёмкой. При продолжении получи свежий snapshot, проверь сохранённые полные источники и остаток. Raw status, unknown maturity/canonical role и отсутствующие связи остаются явными; не объявляй current/base/proposed revision без такого контракта. Если reader недоступен, явно ограниченный прежний путь — `get_node({pid,nodeId})`, каждый `docIds` через `get_doc` и `get_requirements({pid,nodeId,inherited:true})`; он не строгий read-only audit и не единый snapshot. Отсутствующие данные не угадывай. Истина о фиче — в прочитанных источниках, не в title. Дока нет, а логика нетривиальна → первый шаг работы: завести её (Workflow C) из обсуждения/спеки, а не держать в голове. В репо есть свежий локальный граф кода → связи затрагиваемых символов сперва у графа, потом точечный verify по файлам (правила и freshness-check — скил `recursive-context`, references/code-graph.md).

   **Выбор решения до плана/кода.** Проверь применимость сохранённого основания по [solution-discovery.md](solution-discovery.md). Новый существенный выбор требует соразмерной проверки внутреннего, платформенного и внешнего переиспользования; продолжение и известный малый фикс — сверки изменившихся условий, без повторного обзора рынка. Наличие work ID или вход через `next` не заменяют эту проверку.

   **Сложный brief/nextStep.** Перед заявлением о полноте handoff из нескольких применимых источников/variants/сквозных правил выполни [независимую сверку покрытия](context-coverage-review.md): источники → draft review → один repair → проверка сохранения правил. Используй реального доступного исполнителя; непроверенный остаток не разрешает зависимое утверждение о полноте и не блокирует независимо обоснованную работу. Тривиальное чтение одного факта не требует отдельного reviewer.

   Прочитай [traceability.md](traceability.md): встроенный TDD/Trace и требования проекта действуют независимо от сторонних skills; постоянный тест декларирует ID требования. Прочитай `closes` и связанные issue через `get_issues({pid})`; текст проблемы и текущий статус берутся из Архитектора.

2. **По ходу** — всплыло реальное под-разбиение → сформировать дочерние ноды (`build_hierarchy`, см. [forming-nodes.md](forming-nodes.md)). Не давай скоупу жить только в твоей голове. Появился значимый отчёт, исследование, сравнение, дизайн или демо → сохрани доступный артефакт по [user-artifacts.md](user-artifacts.md) через Workflow C и обеспечь его обнаружение из эпика в этом же ходу, не жди закрытия.

3. **Понимание изменилось** — `update_doc` сразу, не «потом». Дока описывает то, что фича делает СЕЙЧАС, а не первую догадку. Нода/дока, которые врут, хуже их отсутствия.

4. **Перед закрытием** — Trace по [traceability.md](traceability.md): синк → связь требование/тест → тесты и гейт в CI → доказательство мутацией → фактические результаты. Затем Workflow A. К этому моменту дока и проверенная приёмка совпадают с реальностью.

## Workflow A — Closing a feature (CLOSE)

Если по работе создан значимый пользовательский артефакт, перед передачей результата проверь его доступность из эпика по [user-artifacts.md](user-artifacts.md). Используй уже сохранённый документ/ссылку; закрытие не требует нового HTML для каждой задачи.

1. **Trace до статуса.** Выполни [traceability.md](traceability.md), прочитай ноду, её требования (включая inherited), их `closes` и `get_issues({pid})`. Составь список **конкретных требований, исполнение которых доказано**: ID → тест → результат гейта/CI → мутация. `approved` означает согласованное требование, а `done` — выполненное; старые `approved`, принадлежность закрытой ноде и waiver не доказывают исполнение. Не переводить inherited или соседние требования в `done` автоматически. Проверь `validate_project`: ошибки целостности исправь до закрытия; выявленное рассогласование статуса issue исправляется шагами 3–5 этого же хода, а не блокирует собственное исправление.

   Уже сохранённый `done` — факт **статуса в Архитекторе**, а не прочитанный отчёт тестов. Если тестовые доказательства старой работы не проверялись, в summary укажи «статус done, доказательства в этом ходу не проверены»; не придумывай прежние прогоны. Исправление ошибочного `closed` на `open` не требует придумывать доказательства закрытой части.

2. **Закрой обычную выполненную ноду.** Для самого managed epic этот legacy вызов запрещён: сначала шаги доказанных requirement updates ниже, затем `submit_review` с актуальными criteria/requirement IDs/artifact/evidence и подтверждение по принятой policy только при поддерживаемом verifier из [epic-flow.md](epic-flow.md). Missing policy/verifier и stale review остаются незавершёнными явно; не поднимай legacy status. Для обычной ноды, если она ещё не `done`, вызвать:
   ```
   mcp__my-architect__complete_task({
     pid, nodeId,
     summary: "<commit SHA> — <one-line outcome> — trace: <requirement IDs → permanent tests; gate/CI results; mutation red → restored green> — waivers/caveats: <list or none>"
   })
   ```
   Проверь ответ. Каскад обычного прогресса останавливается до managed epic; **не меняет статусы требований или issue**. В managed проекте ответ `next_task:null, next_task_reason:EPIC_FLOW_SCOPE_REQUIRED` требует следующего scoped selection, не перехода к глобальной очереди. Legacy summary заменяет description обычной ноды: сохрани исходные scope/acceptance в итоговом тексте либо в прочитанном source doc, не уничтожай их коротким «Merged». Не передавай ID требования как `nodeId` и не дублируй `update_node({status: "done"})`. Уже закрытая обычная нода не требует повторного `complete_task` для ремонта прослеживаемости.

3. **Явно обнови выполненные требования.** Только для ID с доказательствами из шага 1: `update_requirement({pid, requirementId: "<id>", status: "done"})`. Для 2+ требований — `bulk_update_requirements({pid, updates: [{id: "<id>", fields: {status: "done"}}, ...]})`; проверь `successful`/`failed`, повтори только неудачные обновления и перечитай статусы. Непроверенные требования сохраняют прежний статус. Если живая схема MCP не поддерживает `done`, требуется совместимое обновление backend/MCP: не подменяй его `approved` и не заявляй завершённую синхронизацию.

4. **Синхронизируй issue в этом же ходу.** После записей обязательно заново вызови `get_issues({pid})`: `closedBy` содержит все закрывающие требования **и** узлы, включая другие ветки. Для затронутых issue условие закрытия строгое: `closedBy.length > 0 && closedBy.every(link => link.kind === "node" && link.delivered !== undefined ? link.delivered : link.status === "done")`. У managed node используется явный `delivered`, даже если raw status равен `done` или `draft`; обычные узлы и требования требуют `done`. Если для известного managed epic сервер не возвращает delivery, это compatibility gap — не закрывай issue по raw status. Условие выполнено → `update_issue({pid, issueId: "<id>", status: "closed"})`, если ещё открыт. Хотя бы один closing-элемент не завершён → проблема остаётся `open`; перечисли оставшиеся ID, не повышай им статусы ради закрытия. Если такой issue уже `closed`, верни `open` и укажи причину. Закрытый issue без связей также верни в `open` либо восстанови связь только по доказательствам. Не удаляй реальные `closes`, чтобы сделать условие истинным. Проверь ответы и перечитай issue; `closes` само не закрывает проблему.

5. **Обнови производные данные и проверь итог.** После изменения требований/issue выполни **ещё раз** команду синка из local `CLAUDE.md` (Архитектор → индекс), проверь сохранение набора ID и новые статусы/связи. Затем `validate_project({pid})`: `valid: true` и отсутствие ошибок прослеживаемости подтверждаются ответом. Ошибка API, синка или валидации — незавершённое закрытие; зафиксируй точный гэп и продолжай исправление в пределах доказанных данных. Локальный индекс или старый кеш `get_issues` не заменяет свежий ответ Архитектора.

6. **Scan-for-gaps pass.** Перечитать commit body **и** текущий чат-ход. Помечать каждое вхождение: «deferred», «caveat», «known issue», «not yet wired», «to be tested when», «could improve later», «out of scope», «manual probes pending». Каждый помеченный айтем → Workflow B.

7. **Каталог и end-of-turn summary.** Если работа связана с доступным каталогом, обнови описание текущего поведения только в доказанно поставленном объёме по [product-catalog.md](product-catalog.md); не повышай все связанные требования или classification по факту done-ноды. Укажи закрытые ноды и требования с доказательствами, issue ID → фактический статус (для открытых — remaining closing IDs), результат синка и валидации, подтверждённую каталоговую revision или конкретный гэп. Для каждого гэпа: «<X> уже отслеживается в `<node-id>`» либо «новая нода `<node-id>` создана под эпик `<epic-id>`, релиз `<release-id>`». Локально подготовленную или preview-версию не называй опубликованным релизом без фактической публикации.

## Workflow B — Adding a deferred item

0. **Проблема или работа?** Если surfaced gap — конкретная проблема, названная пользователем или мейнтейнером, сначала `get_issues({pid})`: проверь дубликат по смыслу и источнику. Нет дубликата → `add_issue({pid, title, description, source?, reported_at?})`; description — полный текст проблемы, source — ссылка на наблюдение, без переноса протокола интервью. Issue заводится сразу, без эпика и решения о приоритете. Если это долг/инфраструктура без зарегистрированной проблемы, не придумывай issue. Дальнейшие шаги — для планируемой работы по решению; записи о проблеме в производных документах ссылаются на её ID.

1. **De-dup.** Keyword-поиск в кешированном `get_project_context`. Если нашёл draft/in-progress ноду с overlap по тайтлу/описанию ≥60% — **процитировать ID, не создавать**. Дубликаты ломают `get_next_task` (он leaf-first + alpha — дубль может опередить настоящую работу). При поддержке каталога также найди затронутую постоянную фичу глобально через `search_product_features` по [product-catalog.md](product-catalog.md), включая aliases и соседние ветки, без неявного фильтра текущего UI; новая нода долга не создаёт новую product feature автоматически. Подтверждённую/авторизованную связь с созданной работой сохрани через impacts после получения её реального ID.

2. **Parent epic.** Используй подходящий существующий parent из свежей структуры. Долг текущей фичи обычно остаётся в её эпике; cross-cutting работу размещай по подтверждённому охвату. Если поручение разрешает новое оформление, агент сам выбирает обоснованное размещение по preset. Не выдумывай эпик ради отсутствующего поля: сохрани residual, если смысл или полномочия не определены.

3. **Priority + release** — по rubric в SKILL.md: рутинное реши по источникам, неизвестное сохрани явно, реально спорный выбор адресно эскалируй. Не останавливай независимую разрешённую работу.

4. **Создать ноду:**
   ```
   mcp__my-architect__build_hierarchy({
     pid,
     parentId: "<epic-id>",
     tree: [{
       title: "<convention from local CLAUDE.md or asked once>",
       description: "<lead sentence>\n\n**Why:** ...\n\n**How to apply:** ...\n\n**Source:** <commit SHA / chat turn / spec ref>"
     }]
   })
   ```
   Конвенцию тайтлов читай в local `CLAUDE.md` и существующей структуре. Если её нет, используй простое название наблюдаемого результата без выдуманных приоритетных префиксов; новый вопрос о стиле не нужен.

5. **Назначить release:**
   - **Один айтем:** `mcp__my-architect__update_node({ pid, nodeId, release: "<release-id>" })`.
   - **2+ айтемов сразу:** `mcp__my-architect__bulk_update_nodes({ pid, updates: [{ id, fields: { release: "<id>" } }, ...] })`. Атомарный вызов, явно возвращает `successful` и `failed`.
   - **Всегда валидировать:** длина `successful` должна совпасть с числом запрошенных апдейтов, `failed` — пустой. Если нет — ретрай только по failed-ID. Не считать апдейт состоявшимся пока не проверил ответ.

6. **Опционально: requirement.** Если у дефера есть hard testable criterion — `add_requirement` с `type: "FR"` (поведение), `"NFR"` (SLO/качество), `"SAR"` (arch constraint) или `"CON"` (hard constraint).

   Работа закрывает зарегистрированную проблему → укажи `closes: ["<issue-id>"]` на требовании или ноде через поддерживаемый create/update. Связь выводится из подтверждённой приёмки, не из похожего тайтла. Отсутствие закрывающего требования/узла и другие пропуски фиксируются явно по [traceability.md](traceability.md); причина неизвестна — уточни, не выдумывай.

7. **Уже реализованное решение — тот же цикл закрытия.** Если при разборе проблемы найдено уже выполненное решение, сначала проверь Trace, затем выполни **Workflow A, шаги 2–5** в этом ходу: обычная нода `done` либо managed epic с подтверждённым flow delivery → только доказанные требования явно `done` → свежий `get_issues` → `update_issue` по условию завершения **всех** closing-элементов из шага A4 → синк индекса → `validate_project`. Не оставляй подтверждённо устаревший `open` «до следующего прохода». Если завершена лишь часть closing-элементов, issue остаётся `open` с конкретными оставшимися ID. Если работа только заведена, оставь её фактические статусы и после связывания выполни синк и `validate_project`; регистрация работы не является её исполнением.

## Workflow C — Authoring docs as source of truth

Когда у фичи/эпика остаётся только микро-дескрипшен + пара требований — это уровень «assumption». Привязанные к ноде md-документы превращают её в полноценный источник истины (для агентов и для человека в UI). Доступно через `@my-architect/mcp` ≥ 1.4.0.

### Когда писать док

- На ноде есть нетривиальная логика, которой нет места ни в title, ни в коротком description.
- Закрываешь эпик/фичу и есть «как именно мы это решили» / ADR-материал.
- Заказчик спрашивает «что именно делает <фича>?» — ответ должен жить в репо, не в чате.
- Получен значимый пользовательский артефакт (отчёт, исследование, tradeoff, дизайн, демо/прототип) — применяй [user-artifacts.md](user-artifacts.md): существующая работа, один оригинал, доступная ссылка или HTML-превью и путь из эпика. Не каждый ответ/правка кода требует новый документ.

### Workflow

1. **На старте задачи** — после проверки scope/claim (для managed epic) либо обычного `start_task` прочитать `get_node({pid, nodeId}).docIds` и нужные доки через `get_doc({pid, docId})`. Это исток правды о фиче; не догадываться по title. Правка scope/требований после review требует новой актуальной проверки; сохранение doc само по себе не свидетельство внешней поставки.

2. **Авторинг** — `create_doc({pid, title, content, nodeId})`. Маркдаун; ведущий `# Title` добавляется автоматически, если его нет. Без `nodeId` — проектный док (PRODUCT, ARCHITECTURE и т.п.). Под одной нодой можно много доков.

3. **Правка** — перечитай известный документ, затем `update_doc`: адресные `find` + `replace` или `section` + `sectionBody`, либо полный `content` с сохранением незатронутых разделов; ровно один режим за вызов. Полный `content` заменяет содержимое целиком; title берётся из ведущего `# Heading`. Проверь запись через `get_doc` и привязку через `get_node.docIds`; для пользовательского артефакта обнови существующую ссылку из эпика по shared reference, без дублей.

4. **Перед `complete_task`** — `validate_project({pid})`. Возвращает `{valid, issues[]}`; для каждого issue — `type`, `severity` (error|warning), `nodeId`, `message`. Чинить **минимум** все `dangling-doc-ref` / `dangling-diagram-ref` до закрытия таски. `hierarchy-cycle` / `dangling-parent` — errors, всегда блокируют.

5. **Удаление** — `delete_doc({pid, docId, nodeId})`. `nodeId` обязателен если док привязан к ноде (иначе остаётся в `node.docIds` как dangling). Irreversible.

### Don't (доки)

- **Не дублировать description**. Description — «о чём нода в одну строку», док — «как именно». Если описание влезает в description — не плоди файл.
- **Не писать док без `nodeId`** для фичи/эпика — он повиснет в проекте, и `validate_project` не поймает его как осиротевший.
- **Не игнорировать issues валидатора** перед `complete_task` — это не косметика, это битые ссылки в источнике истины.

## Workflow I — Authoring an initiative (DECIDE · гейт перед оформлением)

Оформляет **ценность и решение «делать ли»** структурной работы — до того, как она станет эпиком/фичей. Правила (гейт 7 вопросов, правила текста, процесс) — в [initiative-gate.md](initiative-gate.md); этот workflow — процедура их применения. Разграничение: skill `design` (форк brainstorming) проектирует **решение** (как строить), initiative — **ценность** (зачем, что теряем, почём).

При доступном каталоге найди существующие возможности глобально (выбранная UI-ветка не ограничивает поиск) и прочитай их источники по [product-catalog.md](product-catalog.md) до интервью: покажи, какие фичи инициатива создаёт/изменяет/выводит, и какой наблюдаемый результат меняется. Предложенные новые фичи/области не считай принятыми; повторно не спрашивай уже принятые решения.

1. **Вход-фильтр «две корзины»** — критерий в [initiative-gate.md](initiative-gate.md). Обычная разрешённая работа → продолжи Z/D без искусственной инициативы. Если запрос только оценочный, верни вывод без записей. Размер/межсервисность не отменяют уже принятое «делаем». Неизвестный факт сначала проверь по источникам; только неразрешённое продуктовое решение требует вопроса.

2. **Решение ещё не спроектировано?** Используй `design` (этот плагин), sketch mode: после исхода/ограничений и [solution-discovery.md](solution-discovery.md) — краткий выбранный подход, затронутые контракты, обратимость и неизвестные затраты. Сравни существующие решения до собственного плана; применимое принятое основание не переигрывай. Это подготовка решения в текущем поручении, не причина остановиться из-за отсутствия внешнего brainstorming skill.

3. **Интервью по 7 вопросам гейта** — по одному вопросу за раз, не анкетой. Автор принёс прозу куском → разложить её по вопросам самому и спрашивать **только дырки** (вопрос, ответ на который уже есть в прозе, не задаётся). Правило фактов: каждый ответ помечается — **факт** (проверяем) / **оценка** (чья) / **цель**. Ответа нет → в текст идёт явный плейсхолдер `[факт: <вопрос>]`, а не правдоподобная заглушка. Не выдумывать. Репозиторий доступен → факты для вопросов 1–3 добывает скил `recursive-context` (рецепт requirements-mining) до интервью; добытое помечается `[факт: код <path>]`.

4. **Краткий выбор.** Собери известные ответы по вопросам гейта. Если нужно ещё непринятое решение, покажи конкретные варианты/последствия и дождись ответа только для зависимого действия. Уже разрешённая работа не проходит новый gate; вопросы о фактах и оформлении не заменяют самостоятельное чтение. «Не делаем» и «не сейчас + наблюдаемый триггер» — легитимные исходы. Запись отложенной работы требует применимого поручения; её наличие не означает разрешение реализовать.

5. **Зафиксируй результат решения.** Если «делать ли»/границы ещё не приняты, покажи конкретный выбор с последствиями и дождись ответа для зависимой реализации. Уже принятое решение не согласуй повторно. Полный текст эпика нужен по задаче: исходная ситуация → было/станет → потребители → что сохраняется → цена ожидания/Опция 0 → аппетит/остаток → обратимость; неизвестные факты остаются явными.

6. **Канон текста — один.** Следуй конвенции проекта; если её нет, используй док на узле. Когда нужен отдельный файл для внешнего читателя/репозитория, выбери обычный путь проекта и сохрани на узле краткий итог с `**Source:** <путь файла>`, без второй независимой копии. Выбор рутинного пути не требует вопроса. Обновляй связанные сведения в том же ходу.

7. **Ноды в my_architect:** `build_hierarchy` по живым `levelNames` (как Workflow Z шаг 2); `add_requirement` на эпик-ноду — проверяемое «станет» → `FR`, kill-критерий → `CON`; `create_doc({nodeId})` из шага 6. При поддержке каталога свяжи полученный ID эпика с принятыми соответствиями product features через impacts по versioned write; незавершённые предложения и ошибку записи покажи явно. Старое дерево ради этой связи не перестраивается.

8. **Финальный самопроход + verify.** Текст против [initiative-gate.md](initiative-gate.md) → Правила текста: стоп-лист, тест переворачиваемости, модальность ЦЕЛЬ/СЕЙЧАС. Незакрытые `[факт: …]` перечислить в выдаче явно — это блокеры публикации. `validate_project` → чисто; echo созданных ID.

## Workflow R — Business-Owner review of an initiative/epic (REVIEW · read-only)

Прогоняет готовый текст эпика/инициативы глазами Business Owner перед публикацией. **Read-only: находит и предлагает — не правит.** Правки вносит автор отдельным ходом и прогоняет ревью повторно.

1. **Вход.** Текст = путь к файлу (`Read`) или my_architect док/нода (`get_doc` / `get_node` + description). Правила прочитать из [initiative-gate.md](initiative-gate.md) — каждый прогон, не по памяти.

2. **Пять проверок** (категории слабостей):
   1. *Generic-фразы* — прогнать по стоп-листу и тесту переворачиваемости из [initiative-gate.md](initiative-gate.md) → Правила текста.
   2. *«Было → станет»* — у каждого пункта ценности есть исходное состояние с фактом и проверяемое целевое. «Разблокирует X» без «сегодня X невозможно потому-то» — слабость. Отдельно: дельта приписана именно этой работе, а не параллельной трансформации (чужую дельту не продаём).
   3. *Статус-кво-тест* — на возражение «и так же работает — зачем трогать?» текст отвечает в том разделе, где заявлена эта ценность, а не полагается на устный комментарий.
   4. *«Если не делать»* — раздел присутствует и отвечает требованиям вопроса 5 гейта ([initiative-gate.md](initiative-gate.md): измеримый тренд, честный do-minimum), а не «будет плохо».
   5. *Внутренние противоречия и регистр* — ценность не заявляет то, что другой раздел называет уже работающим; жаргон без глоссария во входных разделах; артефакт вместо исхода (нет цепочки актор → поведение → сигнал); целевые числа, выданные за текущее состояние.

   Одна слабость — одна категория: относи к первой подходящей проверке по порядку 1→5, в счёте шага 4 слабость не дублируется.

3. **Блокер-скан.** Каждый незакрытый `[факт: …]` — блокер публикации, всегда.

4. **Выход — таблица:** цитата → почему слабо (какое правило гейта) → предложенный фикс **только из фактов самого дока** → `needs_user_fact` (если фикс требует факта, которого в доке нет). Ссылаться цитатами, не номерами строк — номера плывут при правках. В конце — счёт: N блокеров / M рекомендаций.

5. **Не править.** Ни файл, ни док, ни ноды. Предложить автору внести правки и прогнать `/my-architect:bo-review` повторно.

## Description template

Лидируй фактом, потом объясняй:

```
<one-sentence: что отложено / что не работает / что упускается>

**Why:** <user impact или failure mode который оставляем открытым>

**How to apply:**
- <step 1>
- <step 2>
- <acceptance: как поймём что починили>

**Source:** commit <SHA>, chat turn <date>, spec ref <doc §>.
```

## On `plan_release` vs `bulk_update_nodes`

Предпочитать **`bulk_update_nodes`** для массовых release-апдейтов: явный контракт `successful`/`failed`, проще валидировать.

`plan_release` использует тот же bulk endpoint под капотом и должен работать; но в некоторых проектах историчски замечалась частичная запись (см. local `CLAUDE.md` если он явно об этом говорит) — fallback на `bulk_update_nodes` напрямую.

**В любом случае валидировать ответ.** Не доверять `updated: N` без проверки `successful` vs `failed`.
