# Forming nodes — the hierarchy model

Read this when creating nodes (Workflow Z step 2, Workflow B step 4, or any `build_hierarchy` / reclassification).

Уровни, их имена и **глубину** читать live из `get_project_context` (`project.levelNames`) — НЕ хардкодить. Пресет (`scaffold_project({preset})`) задаёт начальные уровни; тип ноды выводится из позиции уровня (`levelNameToType(levelNames, level)`). **Глубина дерева = число уровней** (корень проекта — уровень 1): создание, `build_hierarchy` и `move_node` отклоняют узел ниже последнего уровня (`MAX_DEPTH_EXCEEDED`).

| Preset | Уровни (сверху вниз) |
|---|---|
| `agile` (default) | Epic → Feature → Story → Task → Subtask |
| `safe` | Initiative → Epic → Feature → Story → Task |
| `simple` | Category → Item |
| `custom` | фактические `levelNames` из проекта; см. ограничение создания ниже |

Если работе действительно нужен уровень глубже последнего (например, задачи не помещаются под фичей), добавь его `add_hierarchy_level({ pid, name })` — он встанет в конец списка — вместо того чтобы класть узлы выше их места или в обход предела. Это меняет структуру проекта, поэтому только по нужде текущей работы; имя должно быть новым. При выпуске app 1.12.0 проекты на прежних пресетах и проекты без названий уровней один раз получили уровни своего пресета (и `Level 6…`, если узлы уже лежали глубже); свои названия уровней не менялись. Список `levelNames: []` означает «без предела»: такому проекту уровень не добавить.

Текущий `scaffold_project` не принимает `levelNames`: `custom` создаётся с уровнями по умолчанию, а не с произвольными именами из ответа пользователя. Для собственной структуры сначала установи поддержанный способ её настройки; не выдумывай поле MCP. После создания перечитай реальные уровни через `get_project_context`.

Тесты гранулярности ниже даны на примере `agile`. Для другого пресета **переноси те же тесты** на реальные `levelNames` проекта (в `simple` всего два уровня). **Не ставь узел на уровень, которого нет в схеме:** нужен глубже — сначала `add_hierarchy_level`.

| Уровень | Что это | Тест гранулярности |
|---|---|---|
| **Epic** | крупный исход / направление | объединяет несколько фич; сам не «делается» за один заход |
| **Feature** | отгружаемая способность | одна внятная приёмка; влезает в релиз |
| **Story** | пользовательский срез фичи | «как `<роль>` я `<действие>`, чтобы `<ценность>`» |
| **Task** | ограниченная работа с проверяемым итогом | отдельная приёмка или передача ответственности полезна; число коммитов/PR не задаёт границу |

**Хорошая нода:**

- **Title — имя СУЩНОСТИ, не работы.** Существительное/исход — «что существует, когда готово», а не глагол/шаги/приёмка/перечень. ✅ `Render diagrams from DSL` · `SVG export` ❌ `Frontend: GET .dsl → parse → render (no position persistence)` · `Expose document tools + validate_project via MCP`.
  - **Линт отклонит смелый тайтл** при `build_hierarchy`/`update_node` (RFC-013): стрелки-пайплайны `→…→`, `+`-перечни, матрицы `a/b/c` / `×`, запятые-списки, impl/приёмка в скобках, >10 слов. `(RFC-NNN)` и одиночная стрелка-трансформ — ок. Пиши имя сразу правильно; детали — в description / requirements / дочерние ноды.
- **Description** — лидируй фактом по шаблону (см. [workflows.md → Description template](workflows.md)): что это · **Why** · **How/acceptance** · **Source**. Title = «о чём в строку», doc = «как именно» (Workflow C).
- **Parent** — правильный эпик из live-структуры. **Release** — по согласованному основанию; неизвестный оставь не назначенным.
- **Один уровень granularity на ноду.** Несколько независимых результатов могут требовать дерева; несколько критериев приёмки одного результата сами по себе не требуют детей.

**Минимальная полезная структура.** Один наблюдаемый результат допускает одну ноду по preset; дочерний узел может быть полезен для самостоятельной приёмки, поставки или владения. Не добавляй ребёнка, повторяющего родителя, ради числа уровней; уже существующие узлы и IDs не удаляй. Если обоснованы несколько блоков, `build_hierarchy` строит их подграф одним вызовом:

```
mcp__my-architect__build_hierarchy({
  pid, parentId: "<epic-id>",
  tree: [{ title, type, description, children: [{ title, type, description }] }]
})
```

Сформировал дерево фичи ДО кода → работа идёт против явной структуры, а не «в голове».

**Ошибся типом или местом — ИСПРАВЛЯЙ, не пересоздавай** (RFC-013). Понял по ходу, что «story» на самом деле epic, или нода висит под не тем родителем:

- `move_node({ pid, nodeId, newParentId })` — перенести поддерево (уровни и тип реконсилятся каскадно; циклы и превышение глубины отклоняются; не хватает уровня — `add_hierarchy_level`).
- `set_node_type({ pid, nodeId, type })` — переклассифицировать на месте (id, slug, доки, дети, рефы сохраняются; идемпотентно).

НЕ `delete_node` + создать заново — потеряешь id, доки и историю. `validate_project` подсветит ladder-инверсии (epic под story) — чини их этими туллами.

## Altitude — фича = building block, а не задача

Title-lint выше ловит **формулировку** (имя сущности, не работа). Это — про **высоту**, самый частый провал декомпозиции: фичи/стори режут по **кодовой базе** (слои/сервисы/файлы) вместо **вертикальных building block'ов**.

**Building block** = тончайший независимо поставляемый срез с **наблюдаемым результатом**: после поставки `<актор>` может сделать/увидеть то, чего не мог. INVEST — Valuable, Independent, Testable (демонстрируемый). Building block **МОЖЕТ резать поперёк сервисов** (backend + front + edge); число затронутых компонентов — **не** повод дробить. «1 фича = 1 модуль/сервис» — неверный инстинкт.

| Уровень | Что это | Запах, что на деле задача |
|---|---|---|
| **Feature** | building block — наблюдаемый, независимо поставляемый | «появился класс / поле / endpoint / миграция» |
| **Story** | отдельно **демонстрируемый** под-результат блока | «написать менеджер», «добавить поле», «прокинуть в API» |
| **Task** | ограниченная работа с собственной приёмкой или владением | шаг того же блока без полезной границы ответственности — в acceptance/доке |

**Два теста — прогнать ДО `build_hierarchy` (pre-flight):**

- **Merge-test** (каждая пара предлагаемых соседних узлов): «слить эти два — теряется ли отдельный результат, приёмка, поставка или полезная граница владения?» Нет → это **один** блок. Да → разделение может быть полезно; выбери поддерживаемые preset типы, не называя каждый технический шаг фичей. Разные файлы, исполнители или PR сами по себе не требуют отдельных узлов; существующие IDs и историю сохраняй.
- **Demo-test** (каждая фича): сформулируй демо — «после этого `<актор>` может `<X>`». Если единственное демо — «появился класс/поле/endpoint/миграция» → это **шаг**, слить вверх. Если «админ может объявить слой» / «гость попадает на правильный домен» → это блок.

Сработал хоть один тест на узле — **пере-режь по ценности до записи дерева.**

**Грамматика заголовка (высота).** Заголовок фичи = результат/способность, не артефакт и не действие: ✅ `Админ может объявить слой группы` · `Redirect on auth (L1→L2)` — ❌ `Коллекция domain_tier` · `Поле tier на группе` · `Tier-редирект в create_tokens()` · `добавить/создать/прокинуть …`. (Существительные-артефакты в начале заголовка и глаголы-задачи — запах высоты; `build_hierarchy`/`update_node` возвращают на них `altitude_warnings` — это **предупреждение**, не reject: переименуй в наблюдаемый результат, артефакт оставь в описании.)

**Где живёт «как».** Обычные шаги реализации и `file:line`-якоря — в **описании / доке / acceptance** блока; они **не теряются** — становятся impl-notes. Дочерний узел полезен для отдельного результата, приёмки, поставки или явной границы владения с проверяемой передачей ответственности. Это основание для выбора, не обязательный ребёнок: шаг того же блока без такой пользы остаётся в impl-notes. Тип узла выбирай по preset и смыслу, а не по границе коммита/PR.

**Концептуальный дизайн → HTML, не ASCII (рекомендация).** Нужен UI-wireframe экрана или концептуальная блок-схема для блока — **рекомендуется** самодостаточный fenced `html`-блок с inline CSS в доке узла (Workflow C). Архитектор показывает его в sandbox-iframe; доступны фрагмент и полная HTML-страница. `mermaid`/`box`/ASCII подходят для быстрых набросков и графов связей; концептуальная вёрстка экранов и состояний — HTML. Сохранение оригинала/превью, обнаружение из эпика и проверка — по [user-artifacts.md](user-artifacts.md). JavaScript отключён, но sandbox не гарантирует отсутствие сетевых запросов: авторь без remote assets, tracking, секретов и локальных зависимостей, не обещай полную функциональность приложения.

**Доменно-событийное моделирование.** Выбирай Event Storming для неопределённого порядка событий, переходов состояния или взаимодействия акторов/сервисов; не для каждого эпика автоматически. Используй поддерживаемый `create_diagram({diagramType:'event-storming', nodeId, dsl})` либо блок в доке. DSL: `group`, `[event|command|policy|readmodel|actor|aggregate|external|hotspot]`, `connect`; смысловой поток — команда → событие → политика → следующая команда. `get_diagram.sequence` помогает проверить реальные бреши; исправь их через `update_diagram`, открытые вопросы сохрани hotspots. Валидная схема не доказывает верность смысла. WBS нужен для выбранной декомпозиции, USM — для sourced сценария и срезов; уже имеющееся пригодное представление используй повторно. Неподдерживаемый тип не обходи выдуманным вызовом: сохрани необходимый поток текстом и точный gap.

**Сквозные заботы ≠ фичи.** Инварианты, телеметрия, SLO, раскатка (`shadow→enforce`) — **свойства** блоков, не блоки. Per-block → в acceptance блока; глобальное → в сквозной эпик. Не плодить «фича-инвариант» / «фича-телеметрия».

**Verify before you elevate (не выдумывай интеграцию).** Узел, утверждающий интеграцию — «X читает через Y», «вызывает сервис Z», «завязано на ACP-API» — проверь по **коду** ДО создания. Не подтвердилось (напр. core читает Mongo напрямую, а не через API) → это **открытый вопрос**, а не блок: заведи draft с маркером `VERIFY: <гипотеза>` в описании, не уверенную ноду. Выдуманная интеграция в дереве хуже её отсутствия — она направляет работу не туда (кейс MM 2026-06-24: фиктивный блок «A2» на не-потребляемом ACP-API). Высота — про ценность; это — про **правду**: оба проверяются перед `build_hierarchy`.

**Порядок = зависимости + релизы.** «Сначала контракт, потом фронт» выражается зависимостью и распределением по релизам, а не дроблением блока на узлы-этапы.

**Бюджет гранулярности — запах.** > ~6–8 фич в одном эпике, **или** фичи повторяют структуру кодовой базы (по слоям/сервисам/файлам) — запах горизонтального разреза. Пере-режь по ценности.
