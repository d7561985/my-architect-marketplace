# Несколько физических копий требования — проверка и восстановление

Читай при `REQUIREMENT_ID_AMBIGUOUS`, расхождении чтения после записи или найденных копиях во время миграции. Обычная работа без такого сигнала не требует отдельного полного аудита. Область ремонта определяется поручением; read-only запрос остаётся read-only, независимая разрешённая работа продолжается.

## Сначала наблюдаемая поддержка и состояние

Совместимый сервер отказывает в неоднозначном чтении/записи по ID с кодом `REQUIREMENT_ID_AMBIGUOUS` (HTTP 409). Это не временный сбой для повторения `update_requirement`, bulk или delete. Старый `successful` без совпадающего чтения не доказывает запись. Сохрани точные ID и исход операции; ошибка чтения не означает пустой проект или отсутствие требования.

Поддержку проверяй безопасным вызовом, а не номером плагина или наличием локального имени инструмента:

```ts
inspect_requirement_copies({ pid, requirementIds: selectedIds, offset: 0, limit: 50 })
// requirementIds необязателен, максимум 100 ID; limit 1..100, default 50.
// {schemaVersion:1, supportedActions:['consolidate-identical'], snapshotToken,
//  total, offset, limit, hasMore, counts, items}
```

Используй точный ответ удалённого сервера: ожидаются `schemaVersion: 1` и `supportedActions`, содержащий `consolidate-identical`. 404, `REQUIREMENT_COPY_UNAVAILABLE`, недоступный инструмент или неизвестная схема не означают поддержку; не проверяй её пробной мутацией. `REQUIREMENT_COPY_RESPONSE_INVALID` означает непроверенный ответ, а не пустой inventory или успешный ремонт. Сохрани ограничение и адресные данные для продолжения.

Читай выбранные ID, при inventory — ограниченные страницы до `hasMore:false`. `total` относится к выбранной выборке, `counts` — всему проекту. У каждой страницы свой `snapshotToken`: сравни их; при изменении перечитай нужную выборку, не объединяй окна разных состояний. Это отдельный token, не revision каталога и не migration-audit token. Не усекать необработанный остаток молча.

У item есть `id`, `individualFileCount`, `semanticEqual`, `classification`, `copies`; копии дают `kind`, относительный `path`, `rawHash`, `semanticHash`, `status`, `title`, `ownerNodeId`. Компактный title может быть усечён; для смыслового решения нужны полные исходные записи из поддерживаемого безопасного audit/detail, а не только эти поля.

`duplicate-identical` означает равенство **всех разобранных значений**, включая реестр, если он присутствует: текст, status, ownerNodeId, даты, links, fields и остальные поля. Raw bytes/формат YAML могут различаться. Для consolidation обязательно наличие реестра (`kind: 'registry'`), равного каждому файлу, и минимум двух отдельных файлов. Одного совпадения заголовков или старой пометки «одинаковые» недостаточно. `registry-only`, `file-only`, `normal` не требуют удаления дубликатов.

## Только равные копии — явная ограниченная операция

В разрешённом scope выбери **явные уникальные ID (1..100)** с подтверждённым полным равенством и реестром. До записи сохрани точный request, наблюдённый `expectedSnapshotToken` (64 lowercase hex) и стабильный `operationId` в приватном checkpoint; не генерируй новый ID на каждый retry. Имя операции: 1..100 символов, первая буква/цифра, затем буквы/цифры/`_`/`-`.

```ts
consolidate_requirement_copies({
  pid, operationId, expectedSnapshotToken: inspectedSnapshotToken,
  requirementIds: selectedIdenticalIds
})
// {schemaVersion:1, operationId, status:'completed', replayed,
//  recoveryPath, snapshotToken, consolidated:[{id,retainedPath,removedPaths}]}
```

Сервер сохраняет проверяемые исходные bytes и manifest в приватном recovery-каталоге, затем убирает только лишние равные файлы. Реестр и оставшийся файл не переписываются. Квитанция содержит `recoveryPath`; это серверный приватный путь, не общедоступная ссылка, полный backup проекта или обещание автоматического restore. Сохрани её вместе с исходным request; не публикуй содержимое архива и не удаляй файлы вручную.

- Timeout/502/обрыв после отправки, `REQUIREMENT_COPY_OUTCOME_UNCONFIRMED` или непроверенный ответ writer: результат неизвестен. Повтори **тот же exact request с тем же operationId**, чтобы сервер сверил manifest и завершил/подтвердил эту операцию. Не меняй token/ID list и не начинай новую операцию вместо выяснения исхода. Если проверенный ответ по-прежнему недоступен, сохрани unknown и следующий шаг, не запускай бесконечные retries.
- `REQUIREMENT_COPIES_STALE`: для новой, ещё не начатой операции перечитай состояние и пересчитай выбранные ID; прежний план не подтверждает свежесть. Не подменяй request уже записанной операции.
- `REQUIREMENT_COPY_OPERATION_REUSED`: восстанови сохранённый исходный request; не используй один operationId для другой партии.
- `REQUIREMENT_COPY_RECOVERY_CONFLICT`, `REQUIREMENT_COPY_RECOVERY_INVALID` или `REQUIREMENT_COPY_RECOVERY_INCOMPLETE`: сохрани ошибку/пути/manifest, останови зависимый ремонт и разберись с восстановлением. Не обходи конфликт новым ID или удалением архива. Это не успех и не разрешение перезаписать чужое изменение.

После `completed` заново проверь выбранные ID через inspection и обычное чтение, сравни сохранённые значения; запиши оставшиеся конфликты отдельно. Удаление лишних копий не переводит требование в `done` и не исполняет прежний план статусов. Только затем допустима отдельно обоснованная запись нужных статусов с чтением результата по [Workflow A](workflows.md#workflow-a--closing-a-feature-close).

## Разные значения — полные источники и явное решение

`conflict`, `REQUIREMENT_COPIES_CONFLICT` и изменение хотя бы status/updatedAt исключают `consolidate-identical`, но не запрещают разрешённый адресный ремонт через отдельный `resolve-explicit`. Не выбирай «самое новое», «реестр главный» или «первый файл»; не копируй вариант во все файлы и не используй delete/update для обхода ошибки. Старый план `prev/to/expectTitle`, совпадающие заголовки и сводное число «равных» требований не доказывают состояние сейчас.

Новый путь требует совместимого app/MCP 1.10.0+ и наблюдаемой поддержки удалённого сервера. Обновлённый плагин не обновляет уже запущенный MCP-процесс: после штатного обновления/перезапуска проверь read capability. Старые `inspect_requirement_copies`/`consolidate_requirement_copies` и их `supportedActions:['consolidate-identical']` не меняются; наличие этой capability не доказывает поддержку `resolve-explicit`.

```ts
get_requirement_copy_detail({
  pid, requirementId: selectedRequirementId,
  expectedSnapshotToken: inspectedSnapshotToken, offset: detailOffset, limit: 2000
})
// {schemaVersion:1, supportedActions:['resolve-explicit'], snapshotToken,
//  requirementId, offset, limit, totalChars, hasMore, content}
```

Прочитай **все окна одного snapshotToken** до `hasMore:false`, без пропусков/перекрытий: `offset` следующего окна равен предыдущему `offset + content.length`, полный размер равен `totalChars`. `limit` — число символов (default 2000, максимум 4000), не число источников. Склей `content` в исходном порядке и разбери полученный JSON только целиком: `{id,copies,references,referencePolicy,referenceScope}`. Каждый `copies` содержит прежние metadata и полный `requirement`; `references` содержит `{nodeId,field:'requirementIds'|'requires'}`. Это ссылки иерархии, **не исчерпывающий аудит всех ссылок проекта**: `referenceScope` явно ограничивает результат. Сверь `schemaVersion`, `supportedActions`, requirementId и token в каждом окне. Неполный JSON, stale token или неизвестная схема не дают основания выбрать вариант; перечитай нужную выборку согласованно. Не заменяй полное чтение compact inspection, первым окном, старым локальным export или заголовками.

Для каждого ID сформулируй, какой смысл уже принят и чем это подтверждено:

- **Ранее принятое решение применимо.** Например, полные записи отличаются только status/updatedAt, а сохранённое решение и проверенное evidence уже устанавливают требуемый статус. В пределах порученного ремонта переиспользуй это основание: не спрашивай владельца заново для каждого ID. Выбор обосновывается решением и полными полями, а не самой свежей датой или местом файла.
- **Под одним ID разные требования.** Сохрани нужные варианты отдельными outputs, если их самостоятельный смысл и размещение уже установлены. Явно определи, какой сохраняет исходный ID, какие получают заранее проверенные свободные ID, и куда относятся. Если именно смысл, владелец или назначение входящих ссылок ещё не решены, задай один адресный вопрос с вариантами и последствиями; независимая работа продолжается. Не создавай новый ID на каждый файл автоматически.
- **Нет нужного итогового значения в источниках.** Этот инструмент не редактирует произвольные поля и не исполняет старый status plan. Сначала безопасно восстанови однозначную запись на основании решения, затем отдельным обычным update примени разрешённое изменение с evidence и readback. Не объявляй такой update выполненным заранее.

Составь явный source-bound план: каждый источник из полного detail ровно один раз находится в `outputs` или `archivedSources`. Используй точные `sourcePath`/`path` из detail, включая `requirements/requirements.yaml` для записи реестра выбранного ID (без `#ID`); не собирай путь по догадке. Ровно один output сохраняет исходный ID; прочие `targetId` должны быть явно выбранными свободными ID, а не заменой существующих требований. `ownerNodeId` — подтверждённый существующий узел либо явный `null`; новый владелец не возникает из каталога файла автоматически. Укажи непустые `decisionReference` и `reason`, а для каждого архивируемого источника — причину (каждая строка до 2000 символов). `decisionReference` ссылается на настоящее применимое решение; сама строка не создаёт полномочий. Одна операция содержит 1..100 resolutions, у каждого 1..100 outputs и до 100 archivedSources; не выбирай партию больше реально разобранного scope.

```ts
resolve_requirement_copies({
  pid, operationId: resolutionOperationId, expectedSnapshotToken: inspectedSnapshotToken,
  referencePolicy: 'preserve-existing',
  resolutions: [{
    id: selectedRequirementId, decisionReference: acceptedDecisionReference,
    reason: resolutionReason,
    outputs: [{ sourcePath: chosenSourcePath, targetId: selectedRequirementId, ownerNodeId: chosenOwnerNodeId }],
    archivedSources: reviewedArchivedSources
  }]
})
// Все переменные берутся из полного согласованного detail и принятого решения.
// Пример сохраняет один вариант; для установленного split добавь явные outputs.
// {schemaVersion:1, operationId, status:'completed', replayed, recoveryPath,
//  snapshotToken, referencePolicy:'preserve-existing', resolved:[{id,
//  outputs:[{sourcePath,targetId,ownerNodeId,retainedPath}], removedPaths,
//  referenceReviewRequired, referenceReviewReason}]}
```

До отправки сохрани точный request и стабильный operationId. Сервер архивирует исходные bytes всех затронутых источников и применяет только явно выбранные ID/owner, не переписывая остальные поля выбранного варианта. Архивирование сохраняет исходник, но убирает его из действующих требований: это смысловой выбор, а не разрешение выбросить неизвестную часть. Для неизвестного исхода и recovery-конфликтов действуют те же правила exact request выше; это относится и к `resolve_requirement_copies`. Не заменяй token/operationId при timeout и не обходи несовпадающий архив новой операцией.

`referencePolicy:'preserve-existing'` означает: owned-связи обновляются для заданных outputs, но `requires`, traces, каталог и документы **не перенаправляются молча** на новые ID. При split входящие ссылки на исходный ID остаются на нём; это не доказывает, что их смысл теперь верен. Прочитай `referenceReviewRequired`/`referenceReviewReason` в квитанции, проверь затронутые ссылки и исправь только обоснованные в разрешённом scope. При изменении владельца или выборе другого смысла проверяй ссылки и без флага split. Запиши нерешённое. Не объявляй split полностью завершённым, пока обязательная проверка ссылок не завершена.

`REQUIREMENT_COPY_INPUT_INVALID` означает неверный план, а `REQUIREMENT_COPIES_NOT_DUPLICATED` — отсутствие нужного состояния для этого ремонта; это не повод создавать копии или переходить к delete/update. Исправляй ещё не принятую операцию по свежим источникам и конкретной ошибке; для уже отправленного request с неизвестным исходом сперва установи его результат. `REQUIREMENT_COPIES_STALE` требует нового чтения для нового плана. Completed replay может отказать при чужом изменении после операции: сохрани расхождение, не перезаписывай его и не считай текущие bytes совпадающими со старой квитанцией.

Проверенная квитанция завершения и восстановимые оригиналы подтверждают операцию хранения. После неё перечитай каждый output ID, owner и полные выбранные поля, inspection оставшихся копий и затронутые ссылки; подтверди отсутствие потерь относительно сохранённого плана. Статус `done` в выбранном источнике сам по себе не доказывает реализацию требования или готовность эпика. Ошибка чтения или несоответствие остаются явными, даже если writer ответил successful.

## Частичный reader — доступные факты, явный остаток

Чтобы конфликт другого ID не скрывал доступную часть проекта, явно запроси новый opt-in reader:

```ts
get_requirements({ pid, view: 'availability' })
// {schemaVersion:1, complete, snapshotToken, total, requirements, conflicts}
```

```ts
get_issues({ pid, view: 'availability' })
// {schemaVersion:1, complete, snapshotToken, issues, requirementConflicts}
```

`complete:false` — частичный результат с конфликтами, не пустой проект, не полный канон и не доказательство отсутствия пропущенных ID. Сохрани envelope целиком, включая `conflicts` (requirements), `requirementConflicts` (issues) и `snapshotToken`; не извлекай один массив как будто он полный. Requirements-view также содержит `total` всех ID проекта: доступные строки полного project-view и conflicts вместе должны учитывать каждый ID; node-filter не меняет project-wide metadata. Если сопоставляешь requirement-основания requirements/issues, tokens должны совпадать. Token охватывает требования и иерархию, **не текст issues и не epic-flow**; его совпадение не доказывает атомарный снимок всего проекта или готовность к закрытию. Старые вызовы без `view` остаются строгими; не заменяй отказ обычного reader на пустой список. Поддержку нового ответа проверь явно; старый сервер может не понять параметр, а неизвестный/неверный envelope не считать успешным partial read.

Используй доступные записи для независимой разрешённой работы, навигации и адресного плана. Их недостаточно для полной замены реестра/производного индекса, удаления «отсутствующих» требований или выводов о готовности/закрытии issue, requirement, feature либо эпика, если нужные источники конфликтуют или не прочитаны. Не объявляй closure evidence достоверным по частичному issue-view. Прочитанное `done` не заменяет evidence и проверки всех обязательных зависимостей. Требуемые источники для readiness/review/delivery и обычные мутации конфликтующих ID остаются защищёнными.

## Повреждённые источники и продолжение

`REQUIREMENT_SOURCE_INVALID` — повреждённый источник, а не пригодный вариант для выбора. Сохрани проблему и оригиналы; не выдумывай parsed contents и не удаляй файл по совпадающему title. `REQUIREMENT_STORAGE_UNSAFE` требует сохранить проблему пути, не следуя symlink и не удаляя его как «лишний». `REQUIREMENT_STORAGE_LIMIT_EXCEEDED` / `REQUIREMENT_COPY_LIMIT_EXCEEDED` означают, что полный результат не получен; не пропускай источники молча. Уменьши страницу только если ошибка прямо указывает на размер ответа; превышение пределов самого inventory остаётся явным ограничением, которое меньшая страница не исправляет.

Checkpoint: точный pid, область проверки, исходный request/token, поддержка сервера, полные прочитанные sources и решение, различие raw/parsed values, квитанция/recovery, reference review, доступная часть и оставшиеся конфликты, подтверждённые результаты, неизвестный исход и следующий шаг. В разрешённом scope поправь устаревшие локальные рекомендации «все конфликты требуют владельца» или «после обновления повторить запись»: новое продолжение опирается на живую capability, полные источники и уже принятое решение. Сохрани настоящие ограничения пользователя; обновление плагина само по себе не означает ремонт проекта.
