# Несколько физических копий требования — проверка и восстановление

Читай при `REQUIREMENT_ID_AMBIGUOUS`, расхождении чтения после записи или найденных копиях во время миграции. Обычная работа без такого сигнала не требует отдельного полного аудита. Область ремонта определяется поручением; read-only запрос остаётся read-only, независимая разрешённая работа продолжается.

## Сначала наблюдаемая поддержка и состояние

Совместимый сервер отказывает в неоднозначном чтении/записи по ID с кодом `REQUIREMENT_ID_AMBIGUOUS` (HTTP 409). Это не временный сбой для повторения `update_requirement`, bulk или delete. Старый `successful` без совпадающего чтения не доказывает запись. Сохрани точные ID и исход операции; ошибка чтения не означает пустой проект или отсутствие требования.

Поддержку проверяй безопасным вызовом, а не номером плагина или наличием локального имени инструмента:

```ts
inspect_requirement_copies({ pid, requirementIds: selectedIds, offset: 0, limit: 50 })
// requirementIds необязателен, максимум 100 ID; limit 1..100, default 50.
// {schemaVersion:1, supportedActions:['consolidate-identical'], snapshotToken,
//  total, offset, limit, hasMore, counts, items}
```

Используй точный ответ удалённого сервера: ожидаются `schemaVersion: 1` и `supportedActions`, содержащий `consolidate-identical`. 404, `REQUIREMENT_COPY_UNAVAILABLE`, недоступный инструмент или неизвестная схема не означают поддержку; не проверяй её пробной мутацией. `REQUIREMENT_COPY_RESPONSE_INVALID` означает непроверенный ответ, а не пустой inventory или успешный ремонт. Сохрани ограничение и адресные данные для продолжения.

Читай выбранные ID, при inventory — ограниченные страницы до `hasMore:false`. `total` относится к выбранной выборке, `counts` — всему проекту. У каждой страницы свой `snapshotToken`: сравни их; при изменении перечитай нужную выборку, не объединяй окна разных состояний. Это отдельный token, не revision каталога и не migration-audit token. Не усекать необработанный остаток молча.

У item есть `id`, `individualFileCount`, `semanticEqual`, `classification`, `copies`; копии дают `kind`, относительный `path`, `rawHash`, `semanticHash`, `status`, `title`, `ownerNodeId`. Компактный title может быть усечён; для смыслового решения нужны полные исходные записи из поддерживаемого безопасного audit/detail, а не только эти поля.

`duplicate-identical` означает равенство **всех разобранных значений**, включая реестр, если он присутствует: текст, status, ownerNodeId, даты, links, fields и остальные поля. Raw bytes/формат YAML могут различаться. Для consolidation обязательно наличие реестра (`kind: 'registry'`), равного каждому файлу, и минимум двух отдельных файлов. Одного совпадения заголовков или старой пометки «одинаковые» недостаточно. `registry-only`, `file-only`, `normal` не требуют удаления дубликатов.

## Только равные копии — явная ограниченная операция

В разрешённом scope выбери **явные уникальные ID (1..100)** с подтверждённым полным равенством и реестром. До записи сохрани точный request, наблюдённый `expectedSnapshotToken` (64 lowercase hex) и стабильный `operationId` в приватном checkpoint; не генерируй новый ID на каждый retry. Имя операции: 1..100 символов, первая буква/цифра, затем буквы/цифры/`_`/`-`.

```ts
consolidate_requirement_copies({
  pid, operationId, expectedSnapshotToken: inspectedSnapshotToken,
  requirementIds: selectedIdenticalIds
})
// {schemaVersion:1, operationId, status:'completed', replayed,
//  recoveryPath, snapshotToken, consolidated:[{id,retainedPath,removedPaths}]}
```

Сервер сохраняет проверяемые исходные bytes и manifest в приватном recovery-каталоге, затем убирает только лишние равные файлы. Реестр и оставшийся файл не переписываются. Квитанция содержит `recoveryPath`; это серверный приватный путь, не общедоступная ссылка, полный backup проекта или обещание автоматического restore. Сохрани её вместе с исходным request; не публикуй содержимое архива и не удаляй файлы вручную.

- Timeout/502/обрыв после отправки, `REQUIREMENT_COPY_OUTCOME_UNCONFIRMED` или непроверенный ответ writer: результат неизвестен. Повтори **тот же exact request с тем же operationId**, чтобы сервер сверил manifest и завершил/подтвердил эту операцию. Не меняй token/ID list и не начинай новую операцию вместо выяснения исхода. Если проверенный ответ по-прежнему недоступен, сохрани unknown и следующий шаг, не запускай бесконечные retries.
- `REQUIREMENT_COPIES_STALE`: для новой, ещё не начатой операции перечитай состояние и пересчитай выбранные ID; прежний план не подтверждает свежесть. Не подменяй request уже записанной операции.
- `REQUIREMENT_COPY_OPERATION_REUSED`: восстанови сохранённый исходный request; не используй один operationId для другой партии.
- `REQUIREMENT_COPY_RECOVERY_CONFLICT`, `REQUIREMENT_COPY_RECOVERY_INVALID` или `REQUIREMENT_COPY_RECOVERY_INCOMPLETE`: сохрани ошибку/пути/manifest, останови зависимый ремонт и разберись с восстановлением. Не обходи конфликт новым ID или удалением архива. Это не успех и не разрешение перезаписать чужое изменение.

После `completed` заново проверь выбранные ID через inspection и обычное чтение, сравни сохранённые значения; запиши оставшиеся конфликты отдельно. Удаление лишних копий не переводит требование в `done` и не исполняет прежний план статусов. Только затем допустима отдельно обоснованная запись нужных статусов с чтением результата по [Workflow A](workflows.md#workflow-a--closing-a-feature-close).

## Разные значения и повреждённые источники

`conflict`, `REQUIREMENT_COPIES_CONFLICT`, `REQUIREMENT_SOURCE_INVALID` и изменение хотя бы status/updatedAt означают, что автоматическое объединение недопустимо. Не выбирай «самое новое», «реестр главный» или «первый файл»; не копируй вариант во все файлы и не используй delete/update для обхода ошибки. Сохрани все варианты и provenance; действующий инструмент `consolidate-identical` не выполняет смысловое слияние.

`REQUIREMENT_STORAGE_UNSAFE` требует сохранить проблему пути, не следуя symlink и не удаляя его как «лишний». `REQUIREMENT_STORAGE_LIMIT_EXCEEDED` / `REQUIREMENT_COPY_LIMIT_EXCEEDED` означают, что полный результат не получен; не пропускай источники молча. Уменьши страницу только если ошибка прямо указывает на размер ответа; превышение пределов самого inventory остаётся явным ограничением, которое меньшая страница не исправляет.

Старый план записей с `prev/to/expectTitle` — свидетельство намерения, а не разрешение массово повторить его. После прежней частичной записи когда-то равные копии уже конфликтуют. Сначала нужен адресный разбор полного содержимого и способ восстановления без потери; реальный неразрешённый выбор смысла выноси человеку с вариантами и последствиями, применимое ранее принятое решение сохраняй. Не создавай новые ID под каждый вариант автоматически и не объявляй конфликт решённым потому, что один вариант уже выполнен или отменён.

Checkpoint: точный pid, область проверки, исходный request/token, поддержка сервера, различие raw/parsed values, подтверждённые результаты, неизвестный исход и следующий шаг. Локальные рекомендации вида «после обновления плагина повторить запись» замени в разрешённом scope проверкой живой capability и состоянием копий; обновление плагина само по себе серверный дефект не исправляет.
