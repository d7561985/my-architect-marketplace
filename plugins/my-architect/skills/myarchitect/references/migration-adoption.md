# Полный маршрут организации существующего проекта

Читать при поручении организации либо при выявленных унаследованных пробелах в scope задачи по [границе обычной записи и adoption](../SKILL.md#граница-обычной-записи-и-adoption); отдельный migration intent не обязателен. Новая связь разрешённой работы в уже разобранной области не запускает этот маршрут повторно. Безопасный вход предшествует общему project GET. Работай по поручению пользователя и фактам его проекта. Никакой обязательной отраслевой таксономии, глубины карты, numeric WIP или заранее подготовленного пакета от пользователя не требуется. Агент сам проходит discovery → источники → классификация → compose → prepare → review → apply/verify → adoption. Read-only поручение останавливается до prepare/проектных записей с пригодным для продолжения планом.

## 1. Безопасный вход и границы

Установи точный pid через существующую связь/выбор из [setup.md](setup.md); ошибка соединения не означает пустой проект. Для legacy intake первым проектным чтением используй подтверждённый [safe audit](product-migration.md), сохрани snapshot, физические варианты и пробелы. Не начинай с init, sync, doctor, validate или общего project/hierarchy GET: старый backend может ремонтировать исходник. При неподдерживаемом audit сохрани частичный результат и точную missing capability; не проверяй записью и не обходи raw-файлами.

Различи, что поручено: read-only разбор, организация указанного проекта, перенос объявленных источников, либо изменение поведения. Уже данное разрешение сохраняется; не превращай обычное самостоятельное планирование в новый запрос на старт. Доступ к серверу сам по себе не поручение мигрировать все его проекты. Объявленные private источники не расширяй без основания.

## 2. Агент выводит модель из источников

Прочитай дерево и глобальные кандидаты каталога, полные применимые requirements/docs/историю и доступные локальные источники по [product-migration.md](product-migration.md). Сохрани backup и полный local inventory по соответствующим capability. Выдели постоянную возможность, разовое изменение, рабочий срез, исторический материал и ограничение; статус/заголовок/папка этого не решают автоматически.

Выбери стабильные существующие IDs и понятные основные области из языка продукта. Новая область допустима с объяснением границы и источниками; сложный пример из другой отрасли не является шаблоном. Глобальный поиск предшествует новому feature ID. Одна возможность получает одну основную позицию и aliases/tags, сохраняя work/requirement связи. Простому проекту достаточно обоснованной неглубокой структуры.

Разногласие двух применимых источников, неоднозначное объединение/разделение, изменение цели/приоритета или нехватка полномочий — точечная эскалация. Сохрани спорные записи/провенанс и сформулируй конкретный вопрос; продолжи независимый чистый срез. Не выбирай последнюю версию или сервер победителем без основания и не скрывай конфликт новым ID. Исторический несвязанный остаток не делает весь проект немигрируемым.

## 3. Агент составляет и применяет точный пакет

Следуй [migration-package.md](migration-package.md): actual capability v2 → complete source metadata и самостоятельный semantic plan → offline compose (если нужен) → actual prepare → все страницы exact diff/coverage/residual → свежие `reviewBlockers` → authenticated review → apply → fresh verify. При поддерживаемой automation и применимом поручении агент принимает своё обоснованное exact предложение сам. `reviewMode` не заменяет ни пользовательский scope, ни серверные guards. Account-only/legacy mode, actual reject/defer и source conflict обрабатываются явно, без alternative writer.

Сохрани точные requests/IDs/digests до mutations. Неопределённый ответ согласуй по тому же package/operation; не начинай новую миграцию от отсутствующего сообщения. Catalog verify подтверждает только каталоговую дельту и её сохранность, не всю adoption и не готовность продукта.

## 4. Спецификации, current и proposed

После verify читай [product-evolution.md](product-evolution.md), actual capabilities, свежий manifest/revision и exact sections. Для каждой затронутой возможности различи:

| Наблюдаемое состояние | Действие |
|---|---|
| Есть подтверждённая current revision | Сохрани её; source drift и будущая работа — отдельные изменения с точной base. |
| Current отсутствует, есть только статусы, рассказы или непроверенная версия | Оставь current неизвестной. Сохрани sourced proposed/остаток, не конвертируй legacy done в availability. |
| Есть принятой scope будущий срез и существующий work ID | `apply_product_evolution_command` с `propose-change`: полный целевой requirements snapshot, current base либо null, фактические источники и acceptance criteria. Не потеряй неизменённые ограничения. |
| Есть действительно проверенные version, availability и evidence каждого критерия | Только при поддерживаемой authority/policy допустим существующий `confirm-delivery`; прочитай свежий current после receipt. Каталоговый review этого не заменяет. |

Не выдумывай новый эпик/«историческую поставку» только для заполнения current. Когда контракт не позволяет честно представить прежний факт, сохрани источник и явный остаток. Пустой current не доказывает, что работающего поведения нет. Lifecycle и accepted classification — отдельные оси; не выдавай proposed requirement за действующее поведение.

`set-context` сохраняет полные существующие maturity/milestone/documentRoles и меняет только обоснованное источниками. Unknown остаётся null; роли canonical/decision/historical/proposal относятся к точному doc hash/применимому commit. `put-scenario` используй, когда пользовательский путь действительно описан источником: actor, outcome, действия и independently useful slices; не создавай journey из глубины WBS ради заполнения поля. Все evolution команды имеют собственные expectedRevision/operationId и recovery.

## 5. Активная работа и адресный контекст

Прочитай [epic-flow.md](epic-flow.md), actual capability/queue/revision, действующие claims/waits/policy. В порученном organization scope сам перенеси явно активные существующие epic/initiative в очередь через `enqueue` с проверяемым nextStep; не enqueues все исторические узлы. Если приоритет источниками не установлен или конфликтует — уточни конкретный выбор, не придумывай порядок. Уже managed записи, чужие claims и история сохраняются.

Отсутствующая delivery policy **не запрещает enqueue/claim/submit_review**. Она ограничивает будущую confirmation. Сохрани адресный residual с недостающим действием; продолжай разрешённую карту, спецификации и активную работу. Не принимай policy через фиктивный account action, не записывай якобы согласованные criteria и не навязывай numeric WIP. Четыре критерия конкретного проекта или разговорное согласие не становятся универсальной сохранённой policy.

Организация очереди сама по себе не берёт всю работу в исполнение. Claim только для реально начинаемой порученной работы, со стабильным request/operationId и прочитанной revision. Child selection требует scopeEpicId/claimId/assignee. `done` старых детей не превращает epic в delivered; очередь и feature slice подтверждаются отдельными протоколами.

Исторический legacy-эпик `done` без найденного основания приёмки — кандидат на [адресную проверку завершения](epic-flow.md#завершение-декомпозиции-и-явная-приёмка-эпика). Прочитай доказательства и различи подтверждённую приёмку, доказанную ошибку и неизвестный исход. Не сбрасывай статусы массово, не enqueues архив ради заполнения доски; изменяй только обоснованную запись в порученном scope с сохранением исходников/истории и проверкой свежего владения. Read-only разбор не разрешает эту запись.

Для выбранной активной работы проверь [scoped-context.md](scoped-context.md): global discovery, точный work/feature target, **весь** mandatory manifest/continuations, current/base/proposed и унаследованные ограничения. Проверь, что новый агент найдёт нужную постоянную фичу и исходные обязательства без плоского повторного дампа. Это проверка читабельности нового состояния, не повтор всей инвентаризации.

## 6. Остаток и передача следующему агенту

Сохрани checkpoint: точный pid; источники/непрочитанные границы; source и catalog/evolution/flow revisions; каждое основание классификации; private requests/receipts/digests; stable IDs; current/proposed/unknown по затронутым фичам; active work/nextStep; конфликты, account holds и вопросы с адресатами; подтверждённые и ещё не выполненные действия. Следующий агент начинает со свежей сверки, а не с повторного создания пакета.

Проверка завершения — смысловая: обязательные источники сохранены, карта обоснована, связи не выдуманы, current/proposed честно различены, активная работа видима, scoped context полон, каждый остаток назван и имеет следующий шаг. Counts, validate_project и успешный apply не заменяют эту проверку. Локальный index/sidecar обновляй только разрешённым контрактом без потери retained IDs, test scope и evidence.

Rollback пакета отменяет только собственный catalog diff. Evolution/flow/local projection — отдельные операции и отдельные checkpoints; их нельзя молча стереть общим backup. Новые ссылки могут правильно заблокировать catalog rollback. Различай «catalog package verified», «adoption выполнена в указанном scope» и «поведение поставлено». Точный оставшийся конфликт или unknown current не скрывай фразой «всё мигрировано».
