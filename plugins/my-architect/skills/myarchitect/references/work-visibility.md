# Accepted work is visible without another permission round

Принятое поручение на реализацию уже разрешает агенту вести эту работу в Architect. Человек наблюдает результат и решает реальные вопросы смысла; он не обязан отдельно говорить «добавь в канбан», `enqueue` или `claim`. Это применяется и к уже начатой разрешённой работе, которая оказалась невидимой на доске. Read-only запрос остаётся read-only. Доступ к серверу, предложение агента и наличие старого backlog сами по себе не являются поручением исполнять его.

## 1. Startup/resume: один переносимый контракт

Claude и Codex читают этот reference при первом входе/продолжении через skill, Z/D или `next`. SessionStart-хук — напоминание, не единственная доставка инструкции: если host не исполняет hooks, выполни тот же read-only check из установленного плагина:

```sh
node "<resolved-plugin-directory>/scripts/workflow-contract.mjs" check
```

Проектный `.architect/agent-workflow.json` хранит `contractVersion:1`, точный `projectId`, `authoritySource`, дату и hashes проверенных `AGENTS.md`/`CLAUDE.md`. Это квитанция адресного пересмотра локальных инструкций, не доказательство прав, свежего сервера, завершённой миграции или истинности текста. Нет квитанции/иная версия/изменился hash → проверь только применимую дельту, не повторяй весь аудит проекта. Ошибка или future schema сохраняются для разбора; не перезаписывай их ради тишины хука.

1. Прочитай текущий запрос, сохранённый checkpoint/принятые owner rules и обе локальные инструкции, если они есть. Установи точный pid по setup. Найди конкретное противоречие, например сгенерированное агентом «owner сам ставит эпики в очередь» при прямом поручении самостоятельно вести реализацию и её видимость.
2. Исправь только доказанно устаревшее правило, с источником принятого поручения и причиной. Прямое актуальное поручение владельца имеет приоритет над противоречащей старой локальной памяткой: не требуй повторного разрешения или доказательства её авторства, если новое указание однозначно. Сохрани остальные реальные ограничения владельца: read-only, release/deploy approval, запрет новых направлений, пределы данных/доступа. Новый плагин сам по себе их не отменяет. Если актуального разрешения недостаточно и происхождение запрета неизвестно, либо актуальные указания реально конфликтуют, задай один конкретный вопрос о зависимом действии; независимая разрешённая работа продолжается. Не объявляй любое неудобное правило «сгенерированным».
3. Сохрани переносимую короткую ссылку в используемых проектом `AGENTS.md`/`CLAUDE.md`: «Accepted implementation work is registered, enqueued and claimed by the agent under myarchitect references/work-visibility.md; preserve explicit owner restrictions. Workflow review: .architect/agent-workflow.json». Не создавай вторую копию всего skill и не правь установленный cache. Если проект использует только один instruction file, достаточно этого файла плюс общего receipt; второй host обязан прочитать binding и этот reference через skill.
4. После смысловой сверки и reread сохрани квитанцию с настоящим источником разрешения (`authoritySource`), не выдуманной ссылкой:

```sh
node "<resolved-plugin-directory>/scripts/workflow-contract.mjs" record --project-id '<verified pid>' --authority-source '<accepted owner instruction or canonical decision reference>'
```

Команда не меняет инструкции сама, не проверяет человеческое согласие и не пишет на сервер. Не запускай `record` ради зелёного check до обзора. При read-only запросе только сообщи несовпадение; исправление инструкций и квитанция ждут разрешённой работы. В следующих сессиях current receipt экономит повторное чтение, но не отменяет свежую сверку task/claim/capability и более поздние прямые указания.

## 2. Принятая задача → соразмерная работа → очередь

До реализации найди существующие work, feature и требования по смыслу/источнику. Нужный active эпик уже есть → используй его и соответствующий child; микроисправление не требует нового эпика, product feature или набора одинаковых требований. Реальный самостоятельный результат без подходящей работы → создай минимальную разрешённую preset структуру, тестируемую приёмку и связь с затронутой постоянной фичей по Z/product-evolution. Technical scope не требует выдуманной продуктовой возможности. Пробел в старой классификации идёт по adoption, не через обход catalog CAS.

Для **этой принятой работы** проверь живой flow/capabilities. Отсутствует entry у подходящего epic/initiative → агент сам сохраняет и выполняет `enqueue` с точным nodeId и полезным `nextStep`; затем сам получает `claim`, если собирается исполнять этот scope. Не ожидай новой команды пользователя после уже принятого задания. Создание ноды, enqueue и claim — разные серверные операции с собственными квитанциями, а не разные человеческие согласования. Достаточно принятого текущего scope; не ставь в очередь все root/старые done/непринятый backlog и не заявляй за них доступность. Новый запрос вне завершённого эпика оформляется как новый подходящий work, а не переписанная история delivered.

Сначала продолжай фактически свой действующий claim. Чужой claim нельзя присвоить по возрасту, одинаковому общему actor `agent` или внешним признакам коммитов. Для независимого разрешённого leaf внутри занятого эпика используй `get_next_child_work` → `claim_child` с собственным session actor; действуй по фактической capability и конфликтам. Coordinator тоже берёт child claim перед исполнением отдельного child; owning epic не делает его владельцем всех детей. Recommendation не равна claim. Scope текущего запроса важнее общей рекомендации очереди: не выбирай чужую/unrelated работу ради непустой доски.

Если обнаружена разрешённая работа другого агента, которая ещё не отражена на доске, можно зарегистрировать/связать подтверждённый scope при соответствующем поручении, но нельзя создать за внешнего агента claim или выдумать его actor, прогресс, тесты и handoff. Сохрани «исполнитель/состояние не подтверждены» и доступные факты; реальный исполнитель должен сверить и получить свой claim. Не отправляй ему сообщение без прямого разрешения пользователя/host.

Неизвестный/unsupported backend → точное ограничение и сохранённый intent, без legacy обхода, повторного запроса разрешения на уже принятую работу или обещания, что очередь обновлена. Независимые разрешённые шаги продолжаются. Missing delivery policy не блокирует очередь/реализацию, но не разрешает принять policy или объявить delivered.

Ошибка source (`REQUIREMENT_ID_AMBIGUOUS`, недоступные требования/спецификации) не является owner gate. Если точные work ID, hierarchy, разрешённый scope и capability уже проверены, выполни поддерживаемые независимые enqueue/claim/progress; сохрани конкретный сбой источника и незавершённый контекст. Приёмка, зависимая реализация, review/delivery ждут необходимых проверенных данных. Не подменяй failed read пустыми требованиями и не обходи guard для зависимого действия; новый вопрос о постановке на доску не исправляет сломанный источник.

## 3. Видимый прогресс во время работы

Для нового progress нужен app/MCP 1.9.5+ и заново запущенный MCP-процесс: обновление plugin cache не обновляет открытый процесс. Новый клиент объявляет поддержку progress протоколу; старому клиенту сервер не предлагает эту команду. Если в истории уже есть progress, старый клиент получает `EPIC_FLOW_CLIENT_UPGRADE_REQUIRED` до новой записи. Обнови и перезапусти клиент, затем перечитай состояние; прежний неизвестный исход восстанавливай только exact replay. Не обходи отказ ручным заголовком из старого клиента и не называй несовместимость отсутствием разрешения владельца.

После значимого результата, смены следующего шага, блокировки и перед handoff/checkpoint обнови тот же канонический документ/артефакт с проверенными фактами. Если live `capabilities.commands` содержит `update_progress`, текущий holder обновляет `nextStep` своего root либо child claim через `{type:'update_progress',nodeId,claimId,nextStep}` с обычными `operationId`, `expectedRevision`, `actor` и readback по [epic-flow.md](epic-flow.md). Не переименовывай других исполнителей и не выпускай/перехватывай claim ради текста. Неизвестный результат → exact replay, известный CAS conflict → fresh reconciliation.

`nextStep` — точное следующее действие, не проценты из головы и не доказательство acceptance. Review, wait, policy и delivery изменяются только своими разрешёнными командами; update_progress не снимает ожидание и не превращает review в delivered. При неподдержанном action сохрани progress в связанном документе и явно оставь board nextStep несинхронизированным; не имитируй поддержку через handoff/reclaim/bulk. Изменений нет → не создавай heartbeat-события ради активности. Человек должен видеть то, что реально принято, выполняется, проверено и остаётся неизвестным.
