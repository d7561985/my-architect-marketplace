# Разбор старого проекта — inventory, предложение, продолжение

Используется, когда существующее дерево смешало возможности продукта, разовые изменения и историю. Цель — проверяемая вложенная карта продукта поверх сохранённых источников. **Full migration apply/rollback tools не реализованы.** Инвентаризация и dry-run не дают разрешения на последующую запись каталога; поддерживаемая авторизованная правка каталога — отдельный путь по [product-catalog.md](product-catalog.md).

Для обычного изменения выбранной фичи/работы сначала используй [scoped-context.md](scoped-context.md), сохраняя глобальный discovery и вложенную Product Map. Новая задача не требует повторить весь migration audit. Адресный context не заменяет inventory/reconciliation старого проекта, полный экспорт или review таксономии; его token и record keys нельзя смешивать с audit token/keys.

## 1. Inventory без мутаций источника

Для строгого dry-run используй уже подтверждённый `pid` из привязки/поручения и проверь его через безопасный audit capability. Не повторяй обычный `get_project_context` только ради Setup, если тот читает legacy metadata с ремонтом. Если привязка отсутствует или конфликтует, сначала разреши точный ID по правилам Setup без пробной мутации; непроверенный проект не сканируй. Сохранённые источники для предложения не подменяют свежую проверку выбранного проекта.

### Поддерживаемый read-only audit

Проверь доступность и фактический ответ `get_migration_audit`. Локальное имя инструмента не доказывает поддержку удалённого backend. Новый контракт:

```ts
get_migration_audit({ pid, input?, section?, offset?, limit?, expectedSnapshotToken? })
// section: sources (default), records, reconciliation, proposals, gaps, findings, taxonomyChanges
// response: {report:{schemaVersion:1, rulesVersion:1, pid, snapshotToken,
//   fullExportComplete:false, canApply:false, scope, counts, taxonomy,
//   projection:'compact', section, items, total, offset, limit, hasMore}}
get_migration_audit_detail({ pid, input?, recordKey, offset?, limit?, expectedSnapshotToken? })
// response: {detail:{snapshotToken,recordKey,encoding:'json',content,totalChars,
//   offset,limit,nextOffset,hasMore}}
```

Первый вызов читает источники без Doctor, миграции layout, синка индекса и записи файлов. `input` — переданные данные сравнения, не путь для сканирования файловой системы агента. Scope: `{nodeIds:[...],includeDescendants:true}`; пустой список даёт общий inventory в объявленных пределах. Метаданные/ID вне выбранного содержания не означают, что все документы прочитаны. Ошибки, неизвестные форматы, пропущенное содержимое и исходные нарушения видны в `sources/gaps/findings`.

`input.localSources` принимает `{id,kind,provenance:{label,reference,sha256?},records:[{kind,id,value}]}`. Источники: `local-index`, `local-export`, `curated`, `retained`, `test-annotations`; kind записи — `requirement` или `test-reference`. Reference — путь относительно проекта; bytes/hashes исходного локального файла агент сохраняет отдельно. Сервер сравнивает переданные records, а не удостоверяет заявленный hash локального файла. Частичная выборка явно описывается в label/checkpoint; отсутствующие local issues/документы не считаются собранными. Вход ограничен 512 KiB; не усекать его молча ради успешного вызова.

Страницы: default20/max100. У каждого компактного item есть `detailKey` и `truncatedFields`; перед смысловым решением дочитай полные нужные поля. Передавай `detailKey` как `recordKey`, читай default2000/max4000 символов по `nextOffset`, затем собирай и разбирай JSON. На всех последующих секциях/окнах передавай **тот же input и snapshotToken первого ответа**, включая offset0 другой секции. При `AUDIT_SNAPSHOT_STALE`/`AUDIT_SOURCE_CHANGED` начни новый report и заново оцени diff; не смешивай старые и новые окна. Изменение scope/local input/proposal тоже меняет snapshot. Snapshot связывает прочитанное содержимое, наблюдаемые метаданные, input и правила; это не механизм редакций спецификаций FR-030. `sources[].sha256` относится к прочитанным bytes (для symlink — к тексту ссылки, без чтения цели), а `metadataFingerprint` — к наблюдаемому stat файла. У пропущенного файла `sha256` может быть null при наличии metadataFingerprint: изменение метаданных инвалидирует snapshot, но не доказывает прочтение или криптографическую сохранность непрочитанного содержимого. Пробел остаётся в report.

`taxonomy` отдельно сообщает observed/proposed counts, `status: not-reviewed | proposed`, `unresolved` и warnings. Проверь не только число фич, но и classified/unclassified, глубину, границы и источники. Даже одна оставшаяся null placement сохраняет `unresolved:true`; причина объясняет остаток, но не устраняет его. Плоский импорт не становится готовым от синтаксической валидности. `input.taxonomy` — `{catalog:<полный ProductCatalogContent v2>,rationale,unclassifiedReasons:{<featureId>:<reason>},flatReason?}`. Существующие IDs/связи сохраняются, изменённая классификация не наследует прежнее принятие автоматически. `flatReason` объясняет простую структуру, не утверждает её за владельца.

Если передан `input.taxonomy`, compact header возвращает `taxonomy.proposalDetailKey`. **Прочитай этот ключ через `get_migration_audit_detail` до review предложения**, передав его как `recordKey` вместе с тем же input и первым snapshotToken. Текущее значение — `taxonomy:proposal`; используй возвращённый ключ. Собери все JSON-окна до `nextOffset:null`: detail содержит точный полный candidate catalog, `rationale`, `unclassifiedReasons` и `flatReason`, если он передан. Compact `taxonomyChanges` показывает изменения фич и их эффективных путей, но не заменяет чтение полного дерева областей и оснований. Отсутствие proposalDetailKey без taxonomy input означает, что этот proposal не был передан, а не что классификация завершена.

Не смешивай два вида ссылок:

- `input.proposals[]` имеет `{id,sourceRefs,role,featureIds,rationale,status}`; role — `product-feature | change | history | constraint | unresolved`, status — `proposed | conflict`. **`sourceRefs` ссылается только на точные `records[].key`**, полученные из inventory, включая local records. Source ID, feature ID, свободная цитата или detailKey другой секции не заменяют record key.
- `input.taxonomy.catalog.areas[].sources` и `features[].sources` сохраняют источники конкретной области/фичи. Для нового ID нужна ссылка, разрешающаяся в прочитанный `sources[].id` либо valid `records[].key` этого snapshot; общий rationale или выдуманная строка не заменяют её и объяснение конкретного parent path. Существование ссылки само по себе не подтверждает смысл классификации.

Перед формированием ссылок дочитай records и нужные details. `validation:invalid`, `contentStatus:out-of-scope|too-large`, конфликт storageId/reportedId и `payloadEncoding:wrapped-json` требуют отдельного разбора; сохранённый malformed ID не является валидным доказательством. Не выбирай победителя среди физических вариантов одного ID по молчанию и не пересоздавай его содержимое.

Этот audit **всегда** сообщает `fullExportComplete:false` и `canApply:false`: он не выдаёт полный backup вложений/истории, не сохраняет серверный пакет и не реализует apply/rollback. Сохрани derived report и входной proposal отдельно для следующей сессии. 404, invalid schema и ошибка доступа остаются ошибкой/неустановленной поддержкой; не создавай пустой успешный report и не запускай вместо него старые команды с ремонтом источников.

Если проект использует [epic-flow](epic-flow.md), сохрани его capability/revision, реальные claims, policy и полную history/receipts в inventory/переносе. Compact pages/detail/history previews не являются полной резервной копией flow. Экспортёр, теряющий registry, останавливает полный transfer до первой lossy destination write. Классификация каталога не enqueues старые эпики и не превращает legacy done в delivered; onboarding — отдельное авторизованное решение.

После Setup зафиксируй полный доступный снимок: проект и его схема уровней/релизов, иерархия, требования с действительными статусами, документы/диаграммы и их связи, issues, существующий каталог. Зафиксируй `remoteSchemaVersion`: нормализованный v2 из удалённого v1 разрешает чтение, но не запись v2. Полный GET и фактический формат источника обязательны; поисковая страница не заменяет inventory. Сопоставь с известными локальными индексами/тестовыми ссылками и RFC/ADR. Каталог архитектуры помогает найти техническую реализацию, но его компоненты не становятся автоматически продуктовыми фичами.

Для каждого источника запиши область выгрузки, время/версию/commit или хеш, фактически полученные ID, пропуски и ошибки чтения. Ограничение по node/status, усечённый ответ или неполная пагинация не являются полным inventory. Сравни **множества ID**, не только количество: увеличившийся набор тоже может потерять старые элементы. Сохрани исторически известные ID с происхождением для отдельного разбора; не восстанавливай их upstream выдуманным содержимым.

Для read-only аудита используй только подтверждённый маршрут без ремонта источника. Обычные legacy project/hierarchy GET и `validate_project` могут запускать миграцию layout или doctor repair; название «get» не доказывает отсутствие записи. Не используй их как запасной путь строгого dry-run. Если безопасный audit capability отсутствует, явно сохрани partial report по уже полученным снимкам/доступным источникам; не пробуй write и не объявляй полный серверный аудит. Уже существующий отчёт валидации можно сохранить как датированный источник. Исходные нарушения и новые proposed conflicts показываются отдельно. Не меняй статусы, не переноси и не удаляй узлы во время классификации. `done`, `archived` в release или слово «фича» в title не устанавливают вид записи и не доказывают доступность продукта.

## 2. Dry run с происхождением решений

Подготовь предложение, которое владелец может проверить без записи. Каждая строка содержит:

| Поле | Содержание |
|---|---|
| Исходная запись | Точный ID, тип, название, фактический статус, ссылка/путь к полному сохранённому тексту |
| Роль | Постоянная возможность, изменение/эпик, срез работы, исторический материал или пока не определено |
| Предлагаемое соответствие | Существующий/новый product feature ID, основной areaId и путь областей (parentId), либо unclassified; отдельно aliases/tags для других способов найти фичу; для работы — смысл creates/changes/retires |
| Основание | Проверяемые источники и границы прочитанного; факт / вывод / решение владельца |
| Неопределённость | Чего не хватает, конкурирующие варианты и последствия выбора |
| Решение | Предложено / принято владельцем / требуется ответ; ссылка на уже полученное решение |

Это **поля review-документа**, не дополнительные поля MCP-каталога. Группировку делай по наблюдаемым возможностям продукта и языку его пользователя. Готовой универсальной таксономии нет. Вложенность — навигация по постоянным областям, а не копия WBS: не создавай обязательную глубокую цепочку или фичу на каждый рабочий узел. Для пересекающих несколько областей возможностей сохраняй один ID и основную область, добавляй обоснованные aliases/tags; перенос не создаёт дубликат. Перед новым ID ищи по всему каталогу, включая другие ветки, aliases и неклассифицированные записи. Не переписывай исходные описания и acceptance; каталог ссылается на них. Предложи небольшой проверяемый срез, сохрани явный список непокрытых и неоднозначных записей.

## 3. Участие человека

Перед вопросами владельцу проверь структуру Product Map по [правилам каталога](product-catalog.md): существующие и предлагаемые пути, стабильные area/feature IDs, сохранённые связи, теги/aliases и точный неклассифицированный остаток. У предложения новой области должны быть родитель, объяснение границы и источник; пустой scoped search расширяется глобально до создания фичи. Перенос родителя показывает изменение путей потомков. Все фичи во flat/Unclassified, нулевые потери ID или просто синтаксически валидный JSON не являются достаточными критериями готовности миграции. Не скрывай этот пробел формулировкой «классифицируем потом». Маленькому продукту допустима обоснованная простая структура без искусственной вложенности.

Владелец определяет ещё не согласованные смысловые границы областей, спорное объединение/разделение возможностей, изменение цели и приоритетов. Уже согласованный принцип группировки позволяет агенту выполнять однозначные размещения; не превращай каждую папку или тег в новый запрос одобрения. Покажи конкретные варианты с последствиями и спроси только недостающие решения. Принятые решения и ранее данное разрешение сохраняются между шагами; не заставляй повторно утверждать каждую однозначную техническую ссылку.

Пока решения нет, классификация остаётся `proposed`, область может быть null. Неопределённые impacts остаются в dry run. Разрешение работать над миграцией не даёт фактов для `accepted` или `available`; переходы опираются на решение и свидетельства соответственно. Публикация предложений в поддерживаемый каталог допустима в уже авторизованном объёме, не требует перестройки старого дерева.

## 4. Checkpoint и возобновление

Храни checkpoint в принятом для проекта review-документе; если конвенции нет, подходит локальный `.architect/product-catalog-review.md`. Это обычный документ, который агент читает и обновляет. Не утверждай, что плагин создаёт его автоматически или сам возобновляет работу.

Checkpoint содержит точную привязку проекта, прочитанные источники и их fingerprints/пробелы, полный сохранённый каталог с revision и remoteSchemaVersion, путь/смысл областей и словарь aliases/tags, dry-run diff, решения владельца, подготовленные стабильные ID/пары impact, результаты каждой попытки записи (ответ/ошибка/неясный исход), **подтверждённые и оставшиеся** партии, baseline валидации и следующий шаг. Снимки могут жить рядом, документ указывает их пути. Без токенов; личные материалы не копируются в публичный plugin repo.

При продолжении:

1. Проверь привязку и заново прочитай удалённый каталог и относящиеся к партии источники.
2. Сравни revision, содержимое и fingerprints с checkpoint; сам checkpoint не является актуальным серверным состоянием.
3. Проверь уже существующие ID/impacts и не повторяй подтверждённые записи. Пересчитай оставшуюся дельту с сохранением чужих изменений.
4. Повторное решение человека нужно только там, где новые данные меняют смысл принятой классификации. В остальных случаях используй сохранённое решение.
5. Обнови checkpoint наблюдаемыми результатами; не пиши «применено» по одному намерению или отправленному запросу.

## 5. Граница поставки и проверка сохранности

Read-only путь заканчивается сохранённым derived report/proposal с fingerprints, пробелами и нерешённой классификацией; исходный проект и локальные индексы остаются неизменными. Не переходи автоматически от успешного dry-run к `replace_product_catalog`.

Отдельная авторизованная правка каталога использует **versioned catalog replacement** из product-catalog reference, затем повторное чтение и сравнение. Ранее выданное разрешение на конкретные proposals/изменения учитывается, повторный общий вопрос не нужен. Перед записью сохрани исходный снимок, но называй его свидетельством и материалом восстановления: один backup не обеспечивает автоматический откат. Принятие таксономии не даёт разрешения на неподдержанный full migration apply.

Сравни исходные ID/тексты/статусы/ссылки и новые каталоговые записи; неизвестные внешние ссылки должны остаться видимыми. Каталожная запись не должна менять старую иерархию и требования. Проверка существующего `validate_project` относится к его реальной области; не выдавай её за проверку миграции или содержания всего каталога.

Полная перестройка/слияние узлов, requirement revisions, атомарное применение к нескольким источникам, hard-delete и автоматический rollback здесь отсутствуют. Не придумывай для них инструменты и не эмулируй откат заменой свежего каталога старым. Если пользователь просит такое действие, подготовь конкретный план и покажи отсутствующую возможность; продолжай независимую разрешённую работу. Полный экспорт/перенос проекта должен сохранить загруженный каталог отдельным артефактом или явно остановиться, если экспортёр его теряет. Снимок требований/issues из traceability init — частный экспорт, не полная резервная копия проекта.

Финальный результат называет проверенный срез, предложенные/принятые классификации, revision после подтверждённой записи, сохранённые источники, неразобранные записи и ошибки. «Предложение сохранено» не равно «миграция завершена», «классификация принята» не равно «поведение поставлено».
