# Рецепт · Code-graph: персистентный граф кода (Graphify-класс)

Модификатор для repo-audit / requirements-mining и Workflow D скила myarchitect — и самостоятельный вход для impact-вопросов по символам («кто зовёт X», «что сломается при смене сигнатуры»): если в репозитории живёт локальный индекс кода — спрашивай сперва его; grep-скоупинг превращается в запрос за секунды, и знание репо переиспользуется между сессиями. Референс-реализация: [Graphify](https://github.com/safishamsi/graphify) — код парсится tree-sitter'ом локально (без API-вызовов), индекс лежит в `graphify-out/graph.json`, свежесть поддерживают git-хуки и `graphify update .`.

## Presence + freshness (первым делом, дёшево)

```bash
[ -f graphify-out/graph.json ] && echo present || echo absent
# свежесть: коммит, на котором собран индекс, против HEAD
B=$(python3 -c "import json;print(json.load(open('graphify-out/graph.json')).get('built_at_commit') or '')" 2>/dev/null)
[ "$B" = "$(git rev-parse HEAD)" ] && echo fresh || echo STALE
```

Свежесть меряй **`built_at_commit` внутри `graph.json`**, а не mtime файла: mtime сдвигает любое касание каталога, и он ничего не говорит о том, с какого дерева собран индекс. Поле пишется при каждой сборке и сравнивается с HEAD точно.

- `absent` → см. «Bootstrap по согласию» ниже: на big-corpus задаче предложи владельцу собрать граф (один раз); отказ → базовые рецепты, без деградации.
- `fresh` → граф — первый источник кандидатов.
- `STALE` → скажи об этом явно и предложи владельцу **`graphify update .`**; кандидатов из протухшего графа помечай «по устаревшему индексу» и не делай по ним выводов без verify по текущим файлам. Если git-хук не установлен — один раз предложи `graphify hook install`, чтобы STALE не повторялся каждую сессию.

> **Команда именно `graphify update .`, а не `graphify . --update`.** Проверено прогоном 22.08.2026: голый путь трактуется CLI как полное извлечение, и на репозитории с документами оно падает с `error: no LLM API key found (481 doc/paper/image file(s) need semantic extraction)` вместо того, чтобы обновить индекс. Форма `/graphify <path> --update` — это слэш-команда скилла, не CLI.

## Карта запросов

| Вопрос | Запрос |
|---|---|
| «что связывает X и Y», обзор подсистемы | `/graphify query "…"` |
| путь / цепочка вызовов между символами | `/graphify path "A" "B"` |
| «что такое X, кто его использует» | `/graphify explain "X"` |
| impact: «кто зовёт X», «что сломается при смене X» | `graphify affected "X"` → verify по задетым файлам |
| сводка по репо: god-ноды, communities, неожиданные связи, suggested questions | прочитай `graphify-out/GRAPH_REPORT.md` — она уже готова, не собирай её запросами |
| структурный доступ (поднят MCP-сервер Graphify) | `query_graph`, `get_node`, `get_neighbors`, `shortest_path` |

### Формулируй запрос ИМЕНАМИ СИМВОЛОВ, а не прозой

Самая дорогая ошибка при работе с графом — задать ему человеческий вопрос. A/B на одном и том же вопросе (ai-video-generator, 9.5к узлов, 22.08.2026):

| Запрос | Что вернулось |
|---|---|
| `graphify query "LibraryModal kindLock onPick uploadArtifact"` | `LibraryModal.tsx`, `api.ts`, `server/index.mjs`, `handleApi()` — ровно нужное |
| `graphify query "как пользователь выбирает картинку из библиотеки медиа"` | маркетинговые доки и чужой `README.md`, кода — **ноль** |

Причина структурная, а не случайная: документов в индексе почти столько же, сколько кода (3870 против 5837), а метки у doc-узлов — это заголовки разделов. Естественно-языковой запрос матчится с заголовками и до символов не доходит. Не знаешь имён — возьми их из `GRAPH_REPORT.md` или одним точечным grep'ом, и только потом иди в граф.

**Убирай из запроса общие существительные — они его отравляют.** Замер 22.08.2026, тот же индекс:
`query "listPrompts createPrompt updatePrompt deletePrompt prompts owner_id"` вернул `src/lg/prompts.ts`
(файл про совсем другое) и родовой узел `Store`; тот же запрос БЕЗ слова `prompts` вернул ровно
`.listPrompts()`, `.getPrompt()`, `.updatePrompt()`, `.deletePrompt()` с номерами строк. Одно
частотное слово перетянуло выдачу на одноимённый файл. Правило: в запросе только различающие имена,
никаких «prompts», «project», «user», «config».

**`graphify explain "<символ>"` часто лучше `query`** — отдаёт точный `файл:строка`, степень связности
и, главное, СПИСОК ВЫЗЫВАЮЩИХ. Когда символ известен, начинай с него, а не с `query`.

## Правило честности (не обсуждается)

Граф — **навигация и кандидаты, НЕ источник фактов**. Ответ графа говорит, КУДА смотреть; фактом становится только подтверждённое живым файлом: контракт `{claim, evidence_path, confidence}` и verify-pass (requirements-mining, шаг 4) действуют без изменений — граф заменяет только шаг скоупинга. Причина: индекс отстаёт от кода между пересборками; решения принимаются по коду, не по индексу.

**Verify — экономно, регионами.** Кандидат графа приходит с `путь:строка` — читай регион вокруг неё (±30 строк через offset/limit или `sed -n`), не файл целиком; целый файл — только когда региона не хватило. Именно этот шаг конвертирует пользу графа в экономию токенов: без него verify съедает всё, что граф сэкономил на скоупинге.

## Композиция: граф заменяет Discovery, а не весь прогон

Правило порядка — граф и `Workflow`/fan-out не конкурируют, они идут последовательно. Ultracode («всегда workflow») и этот скил не противоречат друг другу: **оба, в этом порядке.**

```
graphify query / explain / affected   → ориентация и кандидаты: что где лежит,
                                        с чем связано, куда смотреть      (секунды, дёшево)
        ↓
verify по живым файлам, регионами     → факт становится фактом только здесь
        ↓
Workflow / агенты                     → ТОЛЬКО то, чего граф не знает: поведение кода,
                                        независимые суждения, оценка трудозатрат,
                                        состязательная верификация
```

- **Что граф закрывает:** «какой модуль копировать», «где живёт машинерия X», «что с чем связано», «какие подсистемы вообще участвуют». Это фаза Discovery целиком.
- **Чего граф НЕ даёт:** поведенческих фактов, на которых обычно держится половина ответа («ни один Request не объявляет `$access`», «этот таск не применяет запреты полей», «эти шесть файлов валят линтер»). Это требует чтения тел файлов и/или прогона.
- **Чего граф НЕ ВИДИТ вовсе: символов внутри тел функций.** Экстрактор берёт объявления верхнего уровня и внутрь тела не заходит. Замер 22.08.2026: `LiteGraphView.tsx` — 17 узлов на 4131 строку, и последний из них это сам `LiteGraphView()` на L524, то есть **3600 строк тела компонента дали ноль символов**; верхнеуровневые функции того же файла извлеклись нормально. Плотность по расширениям там же: `.ts` 72.6 узла на 1000 строк, `.mjs` 40.7, `.tsx` 24.1. Практические следствия: (1) для React-компонентов и прочих «толстых» файлов граф отвечает только «в каком файле искать» — дальше сразу поиск; (2) **отсутствие символа в графе не доказывает, что его нет в коде** — это самая опасная форма ложного вывода из графа.
- **Отсюда честная экономия:** порядка половины Discovery, не всего прогона. Не обещай владельцу больше — и не отменяй `Workflow` на основании того, что граф «уже всё рассказал».
- **Антипаттерн, ради которого этот раздел написан:** разослать N агентов грепать структуру проекта с нуля, имея собранный `graphify-out/` в корне. Проверка стоит один `Bash`-вызов; fan-out по уже проиндексированному репо стоит сотни тысяч токенов.

### Формы задач, которые сюда попадают (а выглядят как «не про кодовую базу»)

Оценка трудозатрат · планирование и декомпозиция · ревью · аудит · «где реализовано X» · «что сломается при изменении Y» · онбординг-доки · **написание или обновление `CLAUDE.md`, включая `/init`**.

Каждая из них — Discovery по чужому коду в первой фазе. Классификация задачи по её жанру («это же не вопрос о кодовой базе, а оценка») — типичная точка отказа: решение принимается по **наличию файла на диске**, а не по жанру формулировки.

## Интеграция

- **repo-audit, шаг 0:** партиционирование и карта модулей — из графа (communities, hub-ноды); fan-out дальше как обычно, вопросы агентам уточнены кандидатами.
- **requirements-mining, шаг 0:** скоупинг «какие подсистемы ответят на вопрос гейта» — запросом к графу вместо `git ls-files` + `grep -l`.
- **Написание/обновление `CLAUDE.md` (в т.ч. `/init`) и онбординг-доков:** структура проекта, точки входа, ключевые модули и их связи — из графа и `GRAPH_REPORT.md`; в файл идёт только verified. `/init` — системный промпт, он про граф ничего не знает; вспомнить обязан ты.
- **Workflow D (myarchitect):** взяв ноду в работу при свежем графе — сперва связи затрагиваемых символов у графа, потом точечный verify по файлам; в ноду/доку попадает только verified.

## Bootstrap по согласию (графа нет, а задача big-corpus)

Молча ставить инструмент по-прежнему НЕЛЬЗЯ — но и молча страдать grep'ом не надо. Графа нет, а задача big-corpus класса (аудит репо, requirements-mining, работа по крупному репо)? Предложи владельцу **один раз за сессию**, с честной ценой и выгодой:

> Могу поставить Graphify и собрать граф кода: `uv tool install graphifyy` (или `pipx install graphifyy` — пакет с двумя «y») + `graphify update .` — локально, code-only без API-ключей, сборка за секунды; заодно git-хук `graphify hook install` (свежесть + merge-driver). Каталог `graphify-out/`: команде README рекомендует **коммитить** (общая карта для всех, конфликты graph.json решает merge-driver; в .gitignore — только `cost.json`/`cache/`), соло можно и весь каталог в .gitignore. Дальше кандидаты по коду будут приходить из графа мгновенно, знание репо переиспользуется между сессиями. Ставим?

- **«Да»** → выполни всё из предложения: `uv tool install graphifyy` (фолбэк: `pipx install graphifyy`), `graphify update <repo>`, хук, согласованный вариант для `graphify-out/` (коммитить или .gitignore). Продолжай текущую задачу graph-first.
- **«Нет»** → базовые рецепты без деградации; в этой сессии больше не предлагай.
- Предложение — развилка, не гейт: саму задачу не блокируй ожиданием ответа дольше одного вопроса.
- Бонус сборки: `graphify-out/graph.html` — интерактивная силовая визуализация для браузера (владельцу бывает полезнее твоего текстового ответа). **Но только пока граф меньше 5000 узлов** — см. грабли ниже.

## Известные грабли эксплуатации (замерено 22.08.2026)

**Визуализация тихо исчезает на больших графах, и старый файл при этом удаляется.** Потолок — 5000 узлов. Выше него хук печатает в лог `Skipped graph.html: Graph has N nodes - too large for HTML viz (limit: 5000)` **и стирает ранее собранный `graph.html`** (`watch.py`, ветка `except ValueError` → `stale.unlink()`). Владелец видит только то, что картинка, которая была, пропала — без единого сообщения в терминале, потому что пересборка идёт отсоединённым фоновым процессом. Лечится переменной, которую хук унаследует:

```sh
# в .git/hooks/post-commit и post-checkout, сразу после export PYTHONHASHSEED=0
export GRAPHIFY_VIZ_NODE_LIMIT="${GRAPHIFY_VIZ_NODE_LIMIT:-20000}"
```

Строка не от graphify — её сотрёт повторный `graphify hook install`. Альтернативы, если полный граф в браузере тяжёлый: `graphify tree` (D3-дерево, `GRAPH_TREE.html`, работает на любом размере) или агрегат по сообществам — `export.to_html(..., node_limit=5000)` строит мета-граф, где узел это сообщество, а вес ребра — число межкластерных связей. Учти: **`graphify export html`, который советует SKILL.md, в CLI 0.9.5 отсутствует** — есть только `export callflow-html`; документация разошлась с бинарником внутри одного релиза.

**Вендорные каталоги попадают в индекс и перевешивают свой код.** Механизма ignore у graphify нет. Замер: `node-canvas/.vite/deps/` дал 661 узел, а `@comfyorg_litegraph.js` (644 узла) был самым «густым» файлом проекта в графе — то есть чужой пре-бандл выигрывал выдачу у нашего кода. Лечится удалением каталога и пересборкой: `rm -rf <vendor-dir> && graphify update . --force` (`--force` обязателен: узлов станет меньше, а без него пересборка с уменьшением отказывается перезаписывать граф). Проверять стоит любой каталог сборочных артефактов: `.vite`, `dist`, `coverage`, `.next`.

**В монорепо каждый вызов из подкаталога падает.** `graphify` ищет `graphify-out/` относительно
ТЕКУЩЕГО каталога, а индекс лежит в корне репозитория. Работаешь в `<repo>/<subproject>/` — получаешь
`error: graph file not found`, и лёгко принять это за «графа нет» (замер 22.08.2026). Лечится явным
адресом: `graphify explain "X" --graph <repo>/graphify-out/graph.json`. Флаг `--graph` есть у `query`,
`explain`, `path` и `affected`.

**Экспортируемые константы верхнего уровня в граф не попадают.** Проверено 22.08.2026: запрос про
`CONSUMPTION`/`FREE` вернул соседние файлы, но не сами символы, хотя файл в индексе. Экстрактор
публикует функции и классы; `export const X = {…}` и `= […]` — нет. Практическое следствие: реестры
(`CONSUMPTION`, `FREE`, `API_PREFIXES`, `SCHEMA`, таблицы моделей) — ровно те места, куда чаще всего
надо попасть, и их в графе нет. Спрашивай про них именем ФАЙЛА, а дальше читай регионом.

**Журнал пересборок общий на машину и не помечает репозиторий.** Всё пишется в `~/.cache/graphify-rebuild.log` без указания проекта, поэтому у владельца с двумя графифай-репо строки идут вперемешку: подряд встречаются `Rebuilt: 9110 nodes`, `Rebuilt: 405 nodes`, `Rebuilt: 9674 nodes` — и это выглядит как сбой сборки, хотя это просто два проекта. Прежде чем диагностировать «graphify странно собирается», проверь `find ~ -maxdepth 3 -name graphify-out -type d` и сверь размеры. Скачки внутри одного репо объясняет `post-checkout`: смена ветки запускает **полную** пересборку на другом наборе файлов, а не инкремент.
