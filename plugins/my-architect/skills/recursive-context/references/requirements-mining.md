# Рецепт · Requirements mining (факты из кода для требований и гейта инициатив)

Когда формируются требования/инициативы (Workflow Z шаг 3 / Workflow I шаг 3 скила myarchitect) и репозиторий доступен. Цель — ФАКТЫ с доказательствами, никогда — правдоподобный текст.

## Контракт

- **Вход:** вопросы гейта, которые надо заземлить («что уже работает и не трогаем?», «кто потребители API X?», «было → станет»).
- **Выход:** таблица фактов `{claim, evidence_path, confidence: verified|inferred}`.
- **Правило:** утверждение без пути в код — НЕ факт; в документ оно идёт плейсхолдером `[факт: <вопрос>]` (правило фактов initiative-gate), добытое из кода помечается `[факт: код <path>]`.
- **Разметка confidence:** `verified` — агент открыл файл и цитата поддерживает утверждение; `inferred` — выведено из доков/названий без прямой проверки кода. Не смешивать.

## Шаги

0. **Есть свежий локальный граф кода** → [code-graph.md](code-graph.md): скоупинг запросом к графу вместо `git ls-files` + `grep -l`; правило честности графа действует.
1. **Скоуп:** какие подсистемы могут ответить на вопросы? `git ls-files` + `grep -l` по ключевым словам фичи → модули-кандидаты.
2. **Малый корпус** (≤ ~30 релевантных файлов): один агент на вопрос гейта со списком файлов; Workflow не нужен.
3. **Иначе** — канонический скрипт: map-проход на вопрос гейта, schema `{claim, evidence_path, confidence}`.
4. **Verify-pass:** для каждого `verified`-утверждения отдельный агент заново открывает `evidence_path` и подтверждает, что цитата поддерживает claim (adversarial: сомневаешься → понижай до `inferred`).
5. **Передача:** вызывающий (main loop) вкладывает таблицу фактов в промпт диспатчируемого feature-author / initiative-author. Дыры остаются `[факт: …]`-плейсхолдерами — их закрывает автор у пользователя, не выдумка.
