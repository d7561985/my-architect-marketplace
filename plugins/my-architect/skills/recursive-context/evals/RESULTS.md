## RED (code-graph) — 2026-07-03 (до создания references/code-graph.md)

Сценарий кейса 7 живьём: мини-репо (3 исходника, git-история, СВЕЖИЙ фейковый `graphify-out/graph.json` с корректными call-рёбрами) + вопрос «кто потребители getBlockers и что сломается при смене сигнатуры». Baseline-агент (Sonnet, текущий скил без code-graph-рецепта): ответ отличный по содержанию, но дисциплины графа нет — (1) **порядок обратный**: сперва полный grep, граф использован лишь как перекрёстная проверка постфактум (шаг 5 его процесса); (2) **freshness не проверялась вовсе** (mtime vs коммит — ни одной команды); (3) на крошечном репо граф «замечен» только потому, что виден в листинге из 5 файлов — на большом репо ничто не ведёт агента к графу до дорогого grep-скоупинга. Вывод RED: дельта рецепта — порядок (граф → targeted verify), обязательный freshness-check и graph-first скоупинг там, где перебор файлов дорог.

## RED baseline — 2026-07-03 (до создания файлов скила)

Методология: два живых baseline-прогона (субагенты Sonnet, без каких-либо файлов скила — их ещё не существовало в момент прогона), сценарии из behavior-evals.json id=1 (giant-file, реальная фикстура 600k строк / ~49МБ) и id=5-класса (requirements-mining на реальном репо my_architect). Агентов просили после ответа честно перечислить каждый вызов инструмента.

### Baseline A — giant-file (fixture.log, 600k строк)

Результат: **все 12 иголок найдены**, таймлайн сессии в верном порядке, ноль выдумок, файл целиком не читался (пробы: 20 строк head + 21 tail; дальше — grep/awk/uniq по всему файлу). 7 вызовов инструментов, ~37k токенов.

Дословно из отчёта процесса: `wc -l` → `sed -n '1,20p'` / `sed -n '599980,600000p'` → `grep -oE ... | sort | uniq -c` (уровни, компоненты, статусы) → `grep -n` по редким компонентам → перекрёстные проверки (другие session ID, другие feature-флаги, целостность rid).

**Честный вывод:** на greppable-иголках в однородном машиночитаемом логе компетентный baseline УЖЕ применяет grep-first дисциплину и выигрывает без скила. Это ровно шаг 2 рецепта giant-file («coarse-pass, кандидаты влезли → отвечай напрямую»). Дефициты baseline относительно дисциплины скила: не заявлено покрытие в терминах «что могло быть пропущено» для не-greppable содержимого; подход не масштабируется на задачи понимания (проза/транскрипт, «выжми все решения»), где grep-якорей нет — там нужен fan-out со schema-возвратами, которого baseline не строил и не предложил бы.

### Baseline B — requirements-mining (репо my_architect)

Результат: сильный — факты с путями и номерами строк, сверка с кодом grep'ом, прогон тестов (116/116), проверка npm-версии; 20 вызовов, ~77k токенов, весь корпус протянут через ОДИН контекст.

Дефициты относительно контракта скила: (1) нет структуры `{claim, evidence_path, confidence}` — факты в прозе, confidence не размечен (verified-по-коду vs inferred-из-доков смешаны: значительная часть «фактов» взята из design-доков, а не из кода); (2) нет `[факт: <вопрос>]`-плейсхолдеров для дыр; (3) нет отделённого verify-pass; (4) подход one-context — не масштабируется на большой/незнакомый корпус без доков.

Методологическая деталь: в среде субагентов тул Workflow отсутствует физически — исполнители кейсов 1 и 5 проверили это через ToolSearch и корректно применили задокументированный фолбэк (параллельные plain Agent, изоляция чанк+узкий вопрос, schema-возвраты, ручное покрытие), т.е. фолбэк-ветка скила прошла живую проверку, а не декларативную; кейс 6 проверял фолбэк по определению.

## LIVE — 2026-07-03

### L1 — giant-file end-to-end (фикстура 600k строк / 48.7МБ): PASS 12/12

Исполнено по рецепту giant-file из main loop с настоящим Workflow: размер-гейт (`wc -lc`, пробы 6 строк ≤50) → `split -l 10000` → 60 чанков по ~793КБ → канонический map-reduce скрипт (60 map-агентов Sonnet/low, batch=1, schema `{claim, evidence, chunk}`) → reduce не потребовался (агрегат < 30k). Итог: **ровно 12 находок = все 12 иголок** (4 PANIC TXN-1111/2222/3333/4444; сессия sess-77f3a9 из 5 шагов login→elevate→export→wipe→logout в верном порядке по чанкам 5→16→30→43→55; 3 override slot=1/2/3), каждая evidence байт-в-байт совпала с генератором, ноль выдуманных, покрытие честное: `groupsSucceeded: 60/60, failedGroups: []`. Стоимость: 60 агентов, ~1.22M суб-токенов, ~2.5 мин.

**Живая находка, внесённая в скил (c512e64):** `args` Workflow-скрипта может прийти JSON-строкой, а не объектом — первый запуск завершился с `chunksTotal: 0` за 14мс. Канонический скрипт получил защитный парс `const A = typeof args === 'string' ? JSON.parse(args) : args`.

### L2 — requirements-mining на реальном репо my_architect: PASS

Вопрос гейта: «что уже работает по фиче Open Question & Dependency Gate и не должно быть тронуто?». По рецепту: scope-скан (`git ls-files` + grep по ключам фичи) → 15 релевантных файлов → малый корпус → один mining-агент со списком файлов и строгим контрактом (без Workflow, как и велит шаг 2 рецепта). Итог: **40 фактов, все `verified`, каждый с `evidence_path:строки`** + 2 честных gap-плейсхолдера `[факт: …]` (в т.ч. реальная находка: UI пишет `dependsOn` через локальный store мимо HTTP-роута — вопрос синхронизации двух путей записи) + coverage-отчёт (какие диапазоны читал, какие нет). Выборочный контроль 5 путей контроллером (updateNode-гейт + unsafe-by-omission; bulk deliberate-bypass коммент; 409-маппинг роута; UI-путь записи; sync_diagram_hotspots title-matching) — 5/5 подтверждены дословно. Ноль выдуманных фактов. Косметика: в тексте одного claim опечатка в цитируемом пути дока («superpayers» вместо «superpowers») при корректном evidence_path — ровно тот класс дрейфа, который в бою ловит verify-pass шага 4.

### Вывод RED

Baseline НЕ падает катастрофически на этих сценариях (grep-first у Sonnet уже в крови) — скил нужен не как «спасение от чтения в лоб» в 100% случаев, а как: (1) **контракт** — schema-возвраты, confidence-разметка, verify-pass, плейсхолдеры, заявление покрытия; (2) **fan-out машинерия** для задач понимания без grep-якорей и для корпусов, не влезающих в один контекст; (3) **консистентность** дисциплины между сессиями и тирами моделей. GREEN-прогоны должны показать соблюдение именно этого контракта; live L1 проверяет работоспособность fan-out пути end-to-end.
