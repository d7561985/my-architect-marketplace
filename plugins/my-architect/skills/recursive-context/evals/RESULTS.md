# recursive-context — eval results

## RED baseline — 2026-07-03 (до создания файлов скила)

Методология: два живых baseline-прогона (субагенты Sonnet, без каких-либо файлов скила — их ещё не существовало в момент прогона), сценарии из behavior-evals.json id=1 (giant-file, реальная фикстура 600k строк / ~49МБ) и id=5-класса (requirements-mining на реальном репо my_architect). Агентов просили после ответа честно перечислить каждый вызов инструмента.

### Baseline A — giant-file (fixture.log, 600k строк)

Результат: **все 12 иголок найдены**, таймлайн сессии в верном порядке, ноль выдумок, файл целиком не читался (пробы: 20 строк head + 21 tail; дальше — grep/awk/uniq по всему файлу). 7 вызовов инструментов, ~37k токенов.

Дословно из отчёта процесса: `wc -l` → `sed -n '1,20p'` / `sed -n '599980,600000p'` → `grep -oE ... | sort | uniq -c` (уровни, компоненты, статусы) → `grep -n` по редким компонентам → перекрёстные проверки (другие session ID, другие feature-флаги, целостность rid).

**Честный вывод:** на greppable-иголках в однородном машиночитаемом логе компетентный baseline УЖЕ применяет grep-first дисциплину и выигрывает без скила. Это ровно шаг 2 рецепта giant-file («coarse-pass, кандидаты влезли → отвечай напрямую»). Дефициты baseline относительно дисциплины скила: не заявлено покрытие в терминах «что могло быть пропущено» для не-greppable содержимого; подход не масштабируется на задачи понимания (проза/транскрипт, «выжми все решения»), где grep-якорей нет — там нужен fan-out со schema-возвратами, которого baseline не строил и не предложил бы.

### Baseline B — requirements-mining (репо my_architect)

Результат: сильный — факты с путями и номерами строк, сверка с кодом grep'ом, прогон тестов (116/116), проверка npm-версии; 20 вызовов, ~77k токенов, весь корпус протянут через ОДИН контекст.

Дефициты относительно контракта скила: (1) нет структуры `{claim, evidence_path, confidence}` — факты в прозе, confidence не размечен (verified-по-коду vs inferred-из-доков смешаны: значительная часть «фактов» взята из design-доков, а не из кода); (2) нет `[факт: <вопрос>]`-плейсхолдеров для дыр; (3) нет отделённого verify-pass; (4) подход one-context — не масштабируется на большой/незнакомый корпус без доков.

### Вывод RED

Baseline НЕ падает катастрофически на этих сценариях (grep-first у Sonnet уже в крови) — скил нужен не как «спасение от чтения в лоб» в 100% случаев, а как: (1) **контракт** — schema-возвраты, confidence-разметка, verify-pass, плейсхолдеры, заявление покрытия; (2) **fan-out машинерия** для задач понимания без grep-якорей и для корпусов, не влезающих в один контекст; (3) **консистентность** дисциплины между сессиями и тирами моделей. GREEN-прогоны должны показать соблюдение именно этого контракта; live L1 проверяет работоспособность fan-out пути end-to-end.
